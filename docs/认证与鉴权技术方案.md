## 1. 目标与范围

### 1.1 项目背景

当前 `MyAgentHarness` 为「单机单用户」形态：

- 无用户表、无 `user_id`、无登录页；
- 会话 ID 由服务端 `uuid4().hex` 生成并直接暴露到 URL（`#/c/{thread_id}`）；
- 任何持有 `thread_id` 者即可读、写、删除会话；
- HITL 审批决策不落库，审计链缺失。

### 1.2 本方案目标

在不从零自建密码体系的前提下，引入**自托管开源 IdP** 与**分层授权模型**，使项目从「个人脚本」升级为「可共享的受控服务」。

### 1.3 覆盖范围

| 能力 | 是否覆盖 | 说明 |
| --- | --- | --- |
| 用户注册与生命周期 | ✅ | 由 IdP 提供；应用侧映射 `sub → 本地 profile` |
| 登录 / 登出 / 会话管理 | ✅ | OIDC 流程 + 应用层本地会话 |
| 单点登录（SSO） | ✅ | 通过 OIDC IdP 实现一处登录、多处通行 |
| 令牌管理 | ✅ | Access Token、Refresh Token、ID Token 全生命周期 |
| Web 端认证 | ✅ | Authorization Code + PKCE |
| CLI 端认证 | ✅ | Device Authorization Flow（或 API Key 降级） |
| 机器对机器认证 | ✅ | Client Credentials Flow |
| 权限控制 | ✅ | RBAC + 资源所有权 + 未来可扩展的 ABAC |
| 审计日志 | ✅ | 登录、鉴权失败、HITL 决策、敏感操作全量记录 |
| 运维监控 | ✅ | 指标、健康检查、日志聚合 |

### 1.4 非目标

- 不替换底层大模型后端或修改 `agent/` 核心工具逻辑；
- 不直接对接企业既有 AD/LDAP（可通过 IdP 桥接，本方案只描述 IdP 到应用的接口）；
- 不做容器安全边界（Docker 沙箱仍按现有计划独立演进）。

## 2. 技术选型

### 2.1 候选 IdP 对比

| IdP | 技术栈 | 资源占用 | OIDC | SAML | LDAP | RBAC/ABAC | 适用场景 | 推荐度 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **Authentik** | Python/Django + Go worker | 中等（~1 GB） | ✅ | ✅ | ✅ | ✅ RBAC + 属性策略 | **中小项目、Python 生态友好、现代 UI** | ⭐⭐⭐⭐⭐ |
| Keycloak | Java/WildFly | 高（~1.5–2 GB） | ✅ | ✅ | ✅ | ✅ RBAC + fine-grained policy | 大型企业、复杂联邦 | ⭐⭐⭐⭐ |
| Authelia | Go | 低（~200 MB） | ✅（简单） | ❌ | ✅（只读代理） | 弱，基本 ACL | **仅做反向代理层保护**，不适合作为完整 IdP | ⭐⭐⭐ |
| Zitadel | Go | 中等（~500 MB） | ✅ | 部分 | ❌ | ✅ RBAC + 多租户 | 云原生、多租户 SaaS | ⭐⭐⭐⭐ |
| Dex | Go | 低 | ✅ | ❌ | ❌ | 无（只做联邦代理） | 需要将多个上游 IdP 统一成 OIDC 的网关 | ⭐⭐ |

### 2.2 为什么选 Authentik

1. **Python 生态亲和**：后端语言与本项目一致，出现问题排查成本低。
2. **开箱即用**：OIDC Provider、SAML Provider、LDAP Provider、RBAC、审计日志、MFA、Passkey、WebAuthn 全部内置。
3. **现代 UI 与 API**：管理员界面清晰，提供 OpenAPI 与 Terraform provider，便于自动化。
4. **资源可接受**：单节点部署对开发机与小型 VPS 都友好。
5. **适合演进路径**：前期用 RBAC，后期可通过自定义属性策略平滑扩展到 ABAC。

### 2.3 数据库与缓存选型

| 组件 | 选择 | 理由 |
| --- | --- | --- |
| IdP 主库 | **PostgreSQL** | Authentik 推荐；支持复杂关系、事务、备份 |
| IdP 缓存 | **Redis** | 会话、短期令牌、事件队列缓存 |
| 应用身份映射 | 复用现有 SQLite 或同 PostgreSQL | 前期可用 SQLite，生产建议迁移至 PostgreSQL |
| 审计日志 | PostgreSQL + Loki / 文件日志 | 结构化后落库，便于检索与合规 |

### 3.3 数据流

```
① 用户访问 https://harness.example.com
② 反向代理将请求转发到 MyAgentHarness
③ Auth Middleware 检查 Cookie / Authorization 头
    - 无凭证 → 302 重定向到 Authentik 登录页
    - 有凭证 → 本地验签 / introspection → 生成 Principal
④ 应用用 Principal.user_id 查询 thread_meta，确保只返回该用户的会话
⑤ RunService 启动对话时记录 Principal.user_id 到审计日志
⑥ HITL 中断触发时，将审批决策与 Principal 一并落库
```

### 3.4 集成方式选择

| 方式 | 名称 | 是否推荐 | 说明 |
| --- | --- | --- | --- |
| **A** | 应用作为 OIDC RP | **主推荐** | 应用实现 `/login`、`/callback`、`/logout`；信任链清晰，适合 CLI + Web + M2M 统一 |
| **B** | 反向代理 + Forward Auth | 备选 | Authentik 提供 forward-auth 端点，代理验证后注入头；实现快，但 CLI 需额外处理 |
| **C** | API Key 兜底 | 必要补充 | 给 CLI / CI 在无浏览器环境下的降级方案，需独立鉴权与轮换 |

**本方案主路径为 A（OIDC RP）**，B 作为快速上线备选，C 为 CLI 兜底。

## 4. 认证流程

### 4.1 Web 端：Authorization Code + PKCE

```
① 用户点击登录 / 访问受保护页面
② MyAgentHarness 生成 state、code_verifier、code_challenge
③ 302 重定向至 Authentik：
   /application/o/authorize/
   ?response_type=code
   &client_id=<harness_web>
   &redirect_uri=https://harness.example.com/auth/callback
   &scope=openid profile email harness:threads:read harness:threads:write
   &state=<csrf_token>
   &code_challenge=<S256_hash>
   &code_challenge_method=S256
④ 用户在 Authentik 登录（密码 + MFA / Passkey）
⑤ Authentik 302 回调到 /auth/callback?code=...&state=...
⑥ 应用校验 state，用 code + code_verifier 换 token 三元组
⑦ 应用建立本地 Session-Cookie（HttpOnly Secure SameSite=Strict）
⑧ 后续请求携带 Cookie，应用本地验签或调用 Authentik introspection
```

**安全要点：**

- `state` 必须不可预测且与会话绑定，回调时严格校验；
- `redirect_uri` 必须在 Authentik 中**精确注册**，禁止通配符；
- `code` 一次性使用，超时 60 秒；
- `code_verifier` 不出浏览器；
- Access Token 建议 TTL 5–15 分钟，Refresh Token 7–30 天并启用轮换。

### 4.2 CLI 端：Device Authorization Flow

```
① CLI 调用 POST /application/o/device/
   参数：client_id=harness_cli&scope=...
② Authentik 返回 device_code、user_code、verification_uri
③ CLI 在终端显示：
   请在浏览器打开 https://harness.example.com/if/flow/...
   输入验证码：ABCD-EFGH
④ 用户完成登录/授权
⑤ CLI 轮询 POST /application/o/token/
⑥ Authentik 返回 access_token + refresh_token
⑦ CLI 将 refresh_token 写入用户配置目录，受限权限（0600）
⑧ 后续请求携带 Bearer token
```

**备选降级**：若环境无浏览器，使用**短周期 API Key**（见第 6 节）。

### 4.3 机器对机器：Client Credentials

```
① 脚本向 Authentik 申请 Client Credentials 应用
② 使用 client_id + client_secret（或 mTLS 私钥）请求 token
③ 获得仅含所需 scope 的 access_token
④ 调用 /api/threads 等接口
```

**用途**：CI/CD、定时任务、监控探针、内部 ETL。

### 4.4 SAML 桥接（可选）

若未来需要对接企业 ADFS：

- 在 Authentik 中创建 SAML Provider 作为 Service Provider；
- 企业将 MyAgentHarness 注册为 Relying Party；
- 用户经企业 IdP 认证后，Authentik 将其映射为本地用户并签发 OIDC token 给应用。

应用**不需要**直接实现 SAML，保持单一 OIDC 接口。

## 5. 鉴权模型

### 5.1 总体策略：两层闸门

```
请求 ──▶ ① OAuth Scope 检查（API 入口粗筛）
       ──▶ ② RBAC + Ownership 检查（业务层细筛）
       ──▶ ③ 数据层过滤（按 user_id 查询，PostgreSQL RLS 兜底）
```

### 5.2 OAuth Scope 设计

| Scope | 含义 |
| --- | --- |
| `openid` | OIDC 登录必需 |
| `profile` | 用户名、昵称 |
| `email` | 邮箱 |
| `harness:threads:read` | 读取会话列表与历史 |
| `harness:threads:write` | 发送消息、创建会话 |
| `harness:threads:delete` | 删除会话 |
| `harness:files:read` | 读取工作区文件 |
| `harness:files:write` | 写入 / 修改工作区文件 |
| `harness:admin` | 系统管理 |

**设计原则**：

- 默认 scope 为 `openid profile email harness:threads:read harness:threads:write`；
- `harness:files:write` 等敏感 scope 需 consent 页面显式授权；
- CLI / M2M 的 scope 按最小权限申请。

### 5.3 RBAC 模型

**角色定义：**

| 角色 | 说明 | 默认权限 |
| --- | --- | --- |
| `owner` | 资源拥有者 | 对自己的会话、文件拥有完整 CRUD |
| `admin` | 系统管理员 | 全站会话管理、用户管理、配置管理 |
| `member` | 普通成员 | 创建 / 读取 / 删除自己的会话 |
| `viewer` | 只读成员 | 读取自己的会话历史，不可发送 |

**权限表（Permission → Resource:Action）：**

```python
PERMISSIONS = {
    "thread:read":   "GET /api/threads/{id}",
    "thread:list":   "GET /api/threads",
    "thread:create": "POST /api/threads/{id}/runs",
    "thread:delete": "DELETE /api/threads/{id}",
    "file:read":     "FilesystemBackend read",
    "file:write":    "FilesystemBackend write",
    "file:execute":  "execute tool in sandbox/local mode",
    "system:models": "GET /api/models",
    "admin:all":     "all operations on all resources",
}

ROLE_PERMISSIONS = {
    "viewer": {"thread:read", "thread:list"},
    "member": {"thread:read", "thread:list", "thread:create", "file:read"},
    "admin":  set(PERMISSIONS.keys()),
}
```

**角色到角色的映射位置：**

- 在 Authentik 中创建 Group 或自定义属性 `harness_role`；
- ID Token 或 access_token claim 中携带 `harness_role`；
- 应用中间件读取 claim，解析为本地角色。

### 5.4 资源所有权（Ownership）

所有业务资源表增加 `owner_id` 字段：

```sql
ALTER TABLE thread_meta ADD COLUMN owner_id TEXT NOT NULL DEFAULT '';
ALTER TABLE audit_log   ADD COLUMN owner_id TEXT;
```

**所有权规则**：

```
允许操作 IF user.has_permission(action)
          AND (resource.owner_id == user.id OR user.role == "admin")
```

这是 ReBAC 的最小形态，避免「只要登录就能访问所有 thread_id」的当前漏洞。

### 5.5 未来 ABAC 扩展

当业务出现动态条件时，在 Authentik 中增加自定义属性，并在应用侧扩展策略：

```
允许执行 IF user.department == resource.owner_department
          AND request.time BETWEEN 09:00 AND 18:00
          AND user.trusted_network == true
```

演进顺序建议：**RBAC → RBAC+Ownership → RBAC+Ownership+ABAC 条件**，不要一步到位。

## 6. 安全措施

### 6.1 密钥管理

| 密钥 | 位置 | 管理方式 |
| --- | --- | --- |
| 签名私钥 | Authentik 内部 | Authentik 自动生成与轮换，应用通过 JWKS 公钥端点获取 |
| 应用 OIDC client_secret | `.env` 或 secrets manager | 不提交到代码库；生产用 Docker Secrets / Vault |
| API Key | 应用数据库，哈希存储 | 与密码同等对待，只显示前缀 |
| TLS 私钥 | 反向代理 / Authentik | 由 Caddy/Nginx 自动续期 Let's Encrypt 或企业 CA |

### 6.2 令牌生命周期

| 令牌 | TTL | 吊销 | 存储 |
| --- | --- | --- | --- |
| ID Token | 5–15 分钟 | 不可吊销，靠短 TTL | 不长期存储，仅用于建立本地会话 |
| Access Token | 5–15 分钟 | 靠短 TTL + jti 黑名单 | Web：不存，每次请求 introspection/本地验签；CLI：内存 |
| Refresh Token | 7–30 天 | 轮换 + 重放检测吊销全族 | CLI 配置文件，0600 权限；Web 可不使用（依赖 Session） |
| 本地 Session | 2–8 小时空闲超时，24 小时绝对超时 | 服务端 Redis/DB 删除即可吊销 | HttpOnly Secure SameSite=Strict Cookie |

### 6.3 防重放攻击

- Access Token 携带 `jti`（JWT ID），应用层记录已处理过的 `jti` 一段时间（如 15 分钟）；
- OIDC nonce 防止 id_token 重放；
- 关键写操作（删除会话、审批通过）要求二次校验 `x-request-id` + 幂等 token；
- 所有写接口要求 `state` 或 `nonce` 同源校验。

### 6.4 防 CSRF 与会话安全

- Cookie：`HttpOnly; Secure; SameSite=Strict; Path=/; __Host-` 前缀；
- 登录成功后**重新生成**本地 session_id（防 session fixation）；
- `/auth/callback` 必须校验 `state`，且 `state` 与用户浏览器会话绑定；
- 登出同时清除服务端会话与 Authentik 端会话（若支持 backchannel logout）。

### 6.5 防越权与数据泄漏

- 所有 `thread_id` 查询必须加 `WHERE owner_id = ?`；
- 对 `history()`、`delete_thread()`、`stream()` 等接口统一做 ownership 装饰器；
- 数据库启用行级安全（RLS）作为纵深防御；
- 工具执行结果不得包含用户 B 的数据；
- 审批决策记录当前 `principal.id`。

### 6.6 审计与不可抵赖

创建 `audit_log` 表：

```sql
CREATE TABLE audit_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_type TEXT NOT NULL,      -- login / logout / authz_denied / thread_delete / hitl_decision
    actor_id TEXT NOT NULL,          -- 谁
    target_id TEXT,                -- 对谁
    action TEXT,                   -- 做了什么
    outcome TEXT,                  -- success / denied / error
    ip TEXT,
    user_agent TEXT,
    details TEXT,                  -- JSON
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```
                        │
              ┌─────────▼──────────┐
              │    PostgreSQL      │  ← 主从 / Patroni
              └─────────┬──────────┘
                        │
              ┌─────────▼──────────┐
              │      Redis         │  ← Sentinel / Cluster
              └────────────────────┘
```

### 7.2 MyAgentHarness 无状态化改造

- 当前 SQLite 检查点不利于横向扩展，生产环境迁移到 PostgreSQL；
- 本地会话可外置到 Redis，使应用无状态；
- AgentFactory 缓存、InMemoryStore 保持内存状态，**不要**在多个实例间共享——需在 LB 配置 session affinity（sticky session）或重构为共享存储。

### 7.3 多实例时的注意点

| 组件 | 状态 | 处理 |
| --- | --- | --- |
| Authentik 配置 | 共享 | 通过数据库共享 |
| 应用 Session | 外部化 | Redis / DB |
| Agent 运行状态（RunService._running） | 内存 | 同一用户应路由到同一实例，或改造为分布式锁（Redis/PostgreSQL advisory lock） |
| 长记忆 InMemoryStore | 内存 | 改为持久化 Store（PostgreSQL / Redis） |

### 9.2 风险清单与缓解

| 风险 | 影响 | 概率 | 缓解 |
| --- | --- | --- | --- |
| IdP 单点故障 | 全站无法登录 | 中 | PostgreSQL 主从 + Redis + 多 worker；保留本地应急账号 |
| 令牌泄漏 | 越权访问 | 中 | 短 TTL、Refresh Token 轮换、scope 最小化、绑定 IP/UA |
| redirect_uri 配置错误 | 授权码被截获 | 高（人为） | 精确匹配、无通配符、开发环境独立配置 |

| 性能下降 | 每次请求验签延迟 | 中 | JWKS 本地缓存；Access Token 本地验签；introspection 只在边缘场景 |

### 10.4 FastAPI 认证中间件伪代码结构

```python
# interfaces/web/auth_middleware.py
class AuthMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        # 公开路径直接放行
        if is_public_path(request.url.path):
            return await call_next(request)

        # 从 Cookie 或 Authorization 头提取会话/token
        principal = await extract_principal(request)
        if principal is None:
            return RedirectResponse("/auth/login")

        request.state.principal = principal
        return await call_next(request)

async def extract_principal(request):
    # 优先本地 Session
    session_id = request.cookies.get(SESSION_COOKIE_NAME)
    if session_id:
        return await get_session(session_id)

    # 其次 Bearer token（CLI / M2M）
    bearer = request.headers.get("Authorization", "")
    if bearer.startswith("Bearer "):
        token = bearer[7:]
        return await verify_access_token(token)

    return None
```

> 注：此为**结构示例**，实际实现需包含错误处理、JWKS 缓存、introspection 失败回退、日志与审计。

### 10.5 RBAC 装饰器结构示例

```python
# application/authorization.py
def require_permission(permission: str):
    def decorator(endpoint):
        async def wrapper(*args, **kwargs):
            request = get_request(args, kwargs)
            principal = request.state.principal

            if not principal:
                raise HTTPException(401)

            role = principal.role
            if permission not in ROLE_PERMISSIONS[role]:
                await audit.log("authz_denied", principal.id, action=permission)
                raise HTTPException(403)

            # 所有权校验由业务层根据 resource_id 再次检查
            return await endpoint(*args, **kwargs)
        return wrapper
    return decorator
```

### 10.6 Nginx 反向代理（Forward Auth 备选）

```nginx
server {
    listen 443 ssl;
    server_name harness.example.com;

    location / {
        auth_request /outpost.goauthentik.io/auth/nginx;
        auth_request_set $auth_user $upstream_http_x_authentik_username;
        proxy_set_header X-Authentik-Username $auth_user;
        proxy_pass http://myagentharness:8000;
    }

    location = /outpost.goauthentik.io/auth/nginx {
        internal;
        proxy_pass https://auth.example.com/outpost.goauthentik.io/auth/nginx;
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
        proxy_set_header X-Original-URL $scheme://$http_host$request_uri;
    }
}
```

## 总结

本方案以 **Authentik** 为自托管 IdP，通过 **OIDC Code+PKCE（Web）**、**Device Flow（CLI）**、**Client Credentials（M2M）** 三种方式接入，采用 **RBAC + 资源所有权** 的鉴权模型，配合 **短时效令牌、Refresh Token 轮换、审计日志、Cookie 安全、数据层过滤** 等安全措施，形成从认证到授权、从日志到审计的完整闭环。

实施上建议采用**分阶段交付**：先用 OIDC RP 方式跑通 Web 登录与会话归属（约 2–3 周达成单机可用），再逐步补充 CLI、M2M、审计与 HA。避免一次性引入 ABAC 或复杂策略引擎——认证鉴权是最容易出现过度设计的领域，复杂度应与当前威胁模型和业务规模匹配。
