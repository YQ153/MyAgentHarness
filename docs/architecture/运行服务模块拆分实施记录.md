## 1. 拆分依据

### 1.1 量化事实

| 指标 | 拆分前 |
| --- | --- |
| 行数 / 体积 | 1826 行 / 83.3 KB |
| 同类对比 | 第二大文件 941 行；`application/` 其余 20 个文件中位数约 170 行 |
| 方法数 | 64 个（含 3 个 dataclass、1 个异常类、5 个模块级私有函数） |
| 注释 + docstring | 645 行（**35.3%**）；纯代码 914 行 |
| 最长方法 | `stream` 99 行、`_iterate` 94 行、`resume` 80 行、`__init__` 78 行 |

### 1.2 直接证据：文件内部已有 5 条分节注释

```text
# ---------- 运行            （stream）
# ---------- 编辑与分叉       （regenerate / edit / 分支头 / 分叉点定位）
# ---------- 内部            （_consume / _iterate / _stream_graph / 工具审计）
# ---------- 并发控制         （槽位 / 计数 / 指标 / HITL 挂起登记）
# ---------- 元数据           （轮次 / 用量 / 活动时间）
```

一个类的内部需要用分隔线来分区，本身就是「它已不再是单一职责」的证据。按分区统计：
编辑与分叉 314 行、并发控制与指标 286 行、运行内部实现 319 行、模块级辅助与句柄定义
275 行、运行治理 128 行。

### 1.3 根因

1. **增量式「就近追加」，从未回抽。** 按交付顺序逐项累加：T1 运行登记表、T2 停止、
   T3 审计上下文、T6 指标计数、T7 超时治理与 HITL TTL、T16 编辑分叉、T17 并发上限与
   限流。每一项都要求「运行时的即时状态」，于是全部落在 `RunService` 上，没有任何一次
   把成型的职责迁出去。
2. **三个共享物把职责焊在一起**（拆分的主要阻力）：
   - 一把 `_running_guard` 同时守护运行登记表、五个累计计数、两份 HITL 登记；
   - `RunHandle` 承载停止信号、分叉检查点、用量归属与工具调用草稿，三条入口都靠它传递；
   - `_consume` 是唯一的事件流主脊，用量落库、工具审计、活动时间刷新、分支头刷新、
     槽位释放全挂在它的 `finally` 与顺序点上。
3. **注释密度放大了体积，但它不是负债。** 35% 的注释逐条对应真实踩过的坑（例如
   `_freeze_unrecorded` 的归纳论证、`available_run_slots` 用 `-1` 而非 `0`）。结论：
   减重只能靠**按职责搬迁**，不能靠删注释。

### 1.4 后果

- **测试已经按职责拆开了，生产代码没有**：`test_run_service.py` / `test_run_stop.py` /
  `test_run_limits.py` / `test_run_governance.py` / `test_run_branches.py` /
  `test_run_usage.py` / `test_run_tool_audit.py` / `test_run_counters.py` 八个文件对应一个类。
- 治理巡检与槽位占用、HITL 登记共用临界区，改动一处需同时推理另外两处。

## 2. 拆分结果

| 模块 | 行数 | 函数 | 职责边界 |
| --- | --- | --- | --- |
| `application/run_service.py` | 1303 | 49 | 入口校验、事件流翻译与收尾、审计与用量落库；对外门面 |
| `application/run_registry.py` | 522 | 26 | 运行槽位、累计计数、审批挂起状态的**唯一所有者**（含锁与限流器） |
| `application/run_branch.py` | 322 | 8 | 分叉点定位、分支登记，产出 `ForkPlan` |
| `application/run_governance.py` | 199 | 4 | 超时强制取消、审批挂起 TTL 作废 |

依赖方向（全部发生在 `application` 包内，不涉及任何跨层变化）：

```text
run_service ──┬──> run_registry      （状态与准入）
              ├──> run_governance ──> run_registry      （读快照、写计数）
              ├──> run_branch ──────> run_registry      （占槽位）
              └──> message_utils / audit_recorder
run_governance、run_branch ──> audit_recorder（协议）<── 由 run_service._audit 结构化满足
```

## 3. 契约保持：本方案的核心约束

### 3.1 调用方清单（实测）

| 调用方 | 使用的运行服务成员 |
| --- | --- |
| `application/health.py` | 8 个指标读取（`running_thread_ids` / `started_runs` / `pending_hitl_thread_ids` / `timed_out_runs` / `expired_hitl` / `max_concurrent_runs` / `available_run_slots` / `rejected_runs`） |
| `interfaces/web/routes.py` | `stream` / `resume` / `stop` / `edit` / `regenerate` / `clear_hitl_pending` |
| `bootstrap/web.py` | 把 `enforce_governance` 注册为后台协程 |
| 八个 `tests/application/test_run_*.py` | 公开方法 + 内部入口（`_acquire_run_slot`、`_enforce_run_timeouts`），`service._record_usage` 等 |

### 3.2 做法

- **同名委托**：槽位、计数、HITL 挂起的读写（17 个公开成员）与治理的两个内部步骤
  （`_enforce_run_timeouts` / `_expire_stale_hitl`）在 `RunService` 上保留原方法名与签名，
  方法体是一行委托。**连测试直接驱动的私有入口也保留**——`_acquire_run_slot`、
  `_check_run_limits` 仍是门面的方法（内部调用点亦不变）。
  代价：`run_service.py` 里约 **166 行**是这条契约的显式成本（第 6 节）。
- **再导出**：`RunHandle` / `ToolCallRecord` / `STOP_REASON_STOPPED` / `STOP_REASON_TIMEOUT`
  在 `run_service.py` 上再导出并写入 `__all__`——句柄是 `run_handle()` 的返回类型，
  停止原因是 DONE 事件 payload 的取值，都属对外契约；调用方不该为拿一个类型去耦合实现模块。
- **不动的部分**：`application/__init__.py`、`interfaces/*`、`bootstrap/*`、`runtime/*`、
  `config.py`、八个测试文件、`.importlinter` —— **本次改动 0 行**（除文档）。

### 3.3 过程中修正的两处依赖瑕疵

1. **协作者不得反向依赖上层。** 治理与分叉都要写审计，若直接持有 `RunService` 会形成环。
   改为依赖 `audit_recorder.AuditRecorder` 协议：生产代码传 `RunService._audit`，测试传
   记录用替身，`runtime`/`application` 的依赖方向不受影响。
2. **门面与分叉不再互相 import 私有函数。** 原先 `_same_message_chain` 等 5 个消息工具
   同时被「入口参数解析」与「分叉点定位」使用；下沉到 `message_utils.py`，两侧都只依赖
   一层无状态纯函数。

## 4. 边界取舍：为什么没拆得更细或更彻底

| 决定 | 理由 |
| --- | --- |
| **没有**把工具审计与留存落盘单独成模块（约 190 行） | 它挂在 `_consume` 的收尾链上（`_track_event` 在转发热路径、`_audit_tool_calls` 在流结束后），拆出去必须引入回调契约；收益不抵新增的间接层 |
| **没有**把 `RunRegistry` 提升为 `RunService` 的公开属性 | 那会波及 health / routes / 8 个测试文件约 40 处调用点，属于 **API 变更**，而本次是结构调整。若将来要公开，应作为一次显式决策单独做 |
| **没有**把 `_RunStoppedError` 移出门面 | 它是 `_stream_graph` 与 `_iterate` 之间的控制流协议，两者都在门面内；移出去只会制造一个无意义的共享异常类 |
| **没有**顺手修 `run_service.py` 里其它历史问题 | 拆分与修复混在一起，会让「结构变化是否改变行为」不可判定。唯一例外是补齐迁移后新出现的入参校验（`RunRegistry.acquire`、`prepare_fork`） |

## 5. 验证

| 项 | 命令 | 结果 |
| --- | --- | --- |
| 应用层测试 | `uv run python -m pytest tests/application -q` | **271 passed**（与拆分前基线一致） |
| 全量测试 | `uv run python -m pytest tests -q` | **913 passed**（另有 1 项与本改动无关的环境性失败，见下） |
| 分层契约 | `uv run lint-imports` | **6 kept / 0 broken**（85 个文件、238 条依赖） |

**与本改动无关的既有失败**：`tests/frontend/test_markdown_render.py::test_markdown_suite_passes`
在本机失败，原因是该用例以 `subprocess.run(..., text=True)` 调 node，而 node 输出含中文、
Python 侧按 locale 编码（cp936）解码抛 `UnicodeDecodeError`。已用一条不导入任何
`application` 代码的独立命令复现同一异常，故与本次拆分无关；修法是给那次调用加
`encoding="utf-8"`，属前端测试脚手架，本次未动。

## 6. 规模账（如实记录）

- 单文件：**1826 → 1303 行（-29%）**，函数数 64 → 49。
- 六个模块合计：**2451 行**（比原单文件多 625 行）。
- 增量构成：6 处模块 docstring 与 import 块约 200 行；门面同名委托 **166 行**；
  协议模块 37 行；新增入参校验与拆分说明约 60 行；其余为原注释随实现搬迁时的少量重述。
- 结论：**这次拆分的收益不是「总行数下降」，而是「单模块变更理由唯一」与「可独立阅读 /
  测试」**。`run_service.py` 仍是 `application/` 下最大的文件，但内容已收敛为
  「事件流骨架 + 旁路写入 + 契约门面」；登记表、治理、分叉三块可以脱离事件流单独理解。
