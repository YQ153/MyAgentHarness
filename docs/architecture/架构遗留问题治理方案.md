## 1. 背景与目的

### 1.1 目的

前序重构（2026-09-16 起）解决了层间边界问题。本次评估要回答三个新问题：

1. 前序重构之后，还剩哪些架构问题？
2. 每个问题由哪几行代码举证？
3. 按什么顺序修、拿什么验收？

### 1.2 评估依据

沿用前序文档的三条原则，并补充两条——前三条描述"边界在哪"，后两条描述"边界之外还有什么会腐烂"：

| 原则 | 判定标准 |
| --- | --- |
| **关注点分离** | 每一层只处理一类关注点 |
| **职责单一** | 单个模块的变更理由应当唯一；单文件超过 500 行需给出理由 |
| **依赖方向明确** | 依赖单向收敛，上层可依赖下层，下层不得反向依赖 |
| **规则单一来源** | 同一条业务规则只允许一份实现。允许"委托"（转发调用），不允许"复制"（重写判断） |
| **约定可执行** | 每条架构约定都应有对应契约或测试。**无法被拦截的约定视为不存在**——第五条的引入，正是本次 Q1 的起因 |

### 1.3 量化基线（2026-09-20 实测）

| --- | --- | --- |

### 1.4 对前序一处结论的更正

前一版评估把 `knowledge_runtime.py` 描述为"第二个组装点"。逐行核对后，更准确的说法是：

它是**惰性的进程级服务句柄**，而装配与拆除的**所有权仍在 `bootstrap`**
（`bootstrap/core.py:88` 建起来、`:180-183` 放进 `finally` 拆掉）。所以"两个组装点"
这个说法不成立。

真正成立的问题是：**它不在契约的可校验范围内**（`.importlinter:15-21` 的 `root_packages`
只列了 6 个包），因此"谁能依赖它、它能依赖谁"没有任何约束——这才是方案一要解决的。

> 更正记录保留在此，理由与本文档其余部分一致：把误判写下来，比删掉它更能防止重犯。
> 前序文档 `分层架构评估与重构方案.md` 的历史附注也是同一个处理方式。

## 3. 问题清单

### Q1：架构契约存在覆盖盲区，根级模块是"法外之地"

**现象**：`.importlinter` 的 `root_packages` 只列了 6 个包，根目录 8 个模块全部在可校验范围之外。

**证据**：

```15:21:.importlinter
root_packages =
    agent
    application
    bootstrap
    interfaces
    llm
    runtime
```

根目录实际存在：`config.py`、`main.py`、`knowledge_runtime.py`、`knowledge_tools.py`、
`text_utils.py`、`thread_utils.py`、`web_safety.py`、`web_tools.py`。

其中 `knowledge_runtime.py` 的依赖面最宽——同时 import 应用层、模型层与存储层：

```30:32:knowledge_runtime.py
from application.knowledge_service import KnowledgeService
from llm.embeddings import build_embeddings
from runtime.knowledge_store import open_knowledge_store
```

**根因**：`root_packages` 是按"目录即包"的思路写的，而根级模块恰恰不是包。
于是这些模块的依赖方向既不进依赖图，也不被任何契约约束。

**代价（已真实发生，不是推测）**：`scripts/inspect_thread.py:90-137` 为了不因导入
`knowledge_runtime` 而连带拉起 `application → agent.graph`，被迫**复制**一份
`KNOWLEDGE_DB_NAME` 常量并写导入失败的兜底路径。这是契约盲区逼出来的重复。

**第二处盲区（动态加载）**：自定义工具是**按字符串**加载的（`CUSTOM_TOOL_MODULES`），
`agent/tooling.py:79` 通过 `load_custom_tool_modules` 导入模块名，静态分析看不到这条边。
`tests/test_web_tools.py:24`、`tests/test_knowledge_tools.py:24` 直接
`from web_tools import ...` / `import knowledge_runtime`——这些模块的依赖同样不受约束。

**影响**：

- 契约承诺的"层间不可越界"只对 6 个包成立，根级模块可以任意依赖任何东西
- 新增一个根级模块时，没有任何机制提醒作者"这里也需要约束"
- 插件模块（`web_tools` / `knowledge_tools`）在运行期被加载进 Agent，其依赖面决定了
  一次提示词注入能碰到多少内部实现——目前完全不受控

### Q2：同一条规则存在多份实现，且已经漂移

**现象**：两条规则各有"权威实现 + 复制品"，且复制品已经与权威实现产生可观测差异。

**证据 1 —— 会话 ID 校验规则被抄了一遍**：

```324:333:runtime/usage_store.py
    @staticmethod
    def _validate_thread_id(thread_id: str) -> str:
        if not isinstance(thread_id, str):
            raise ValueError(f"thread_id 必须是字符串，实际：{type(thread_id).__name__}")
        normalized = thread_id.strip()
        if not normalized:
            raise ValueError("thread_id 不能为空")
        if len(normalized) > 128:
            raise ValueError("thread_id 过长")
        return normalized
```

对照权威实现 `thread_utils.py:25-44`：

| 项 | `thread_utils.normalize_thread_id`（权威） | `usage_store._validate_thread_id`（复制品） |
| --- | --- | --- |
| 长度上限来源 | 常量 `MAX_THREAD_ID_CHARS`（`thread_utils.py:17`） | 字面量 `128` 硬编码 |
| 超长报错 | `thread_id 过长（{len} > {MAX}）` | `thread_id 过长`（不含长度） |
| 位置 | 中立模块，三层共用 | `UsageStore` 静态方法 |

同一个包内的另外两处都是**委托**而非复制：

```339:346:runtime/thread_store.py
    @staticmethod
    def _validate_thread_id(thread_id: str) -> str:
        """校验会话 ID 并返回规范化结果。

        Raises:
            ValueError: 为空、非字符串或超出长度上限。
        """
        return normalize_thread_id(thread_id)
```

`runtime/attachments.py:95-110` 同样委托。**同一个 `runtime` 包里，"委托"与"复制"
两种做法并存**——这正是规则即将漂移的标准形态：改 `MAX_THREAD_ID_CHARS` 时，
`usage_store` 不会跟着变，而失效方式是"接口放行、用量入库被拒"这类只在特定
输入长度下才暴露的错误。

**证据 2 —— 截断实现三份，用户可见文案各不相同**：

| 位置 | 签名 | 截断提示 |
| --- | --- | --- |
| `text_utils.py:36`（权威） | `truncate(text, limit)` | `…`（省略号占一个字符） |
| `web_tools.py:102` | `_truncate(text, limit)` | `\n\n... Output truncated at {limit} chars.` |
| `knowledge_tools.py:55` | `_truncate(text)`（用模块常量） | `…（片段已截断）` |

三者的**截断语义**（保留多少字符、是否把提示算进上限）与**提示语**都不同。
差异本身可以是有意的（面向模型的工具输出与面向界面的标题，阈值与措辞本就该分开），
但**判断逻辑**没有必要各写一份。

### Q3：两个入口的认证路径没有收敛（安全相关）

**现象**：装配已经收敛到单点，但认证语义没有。

`bootstrap/core.py:3-5` 写下收敛装配的理由，原文点名了要避免的风险：

```3:5:bootstrap/core.py
WHY 收敛为单点：装配逻辑一旦出现两份副本，新增一个 store 参数就必须同步
修改两处，任何一处遗漏都会造成「Web 有审计、CLI 无审计」这类安全盲区，
而这类差异难以通过功能测试发现。
```

**而认证路径正是这样的两份副本**：

| 步骤 | CLI（`interfaces/cli.py:149-176`） | Web（`interfaces/web/auth/deps.py:77-143`） |
| --- | --- | --- |
| dev key 比对 | `secrets.compare_digest`（`:159`） | `secrets.compare_digest`（`:88`） |
| 查存储 | `api_key_store.validate`（`:167`） | `store.validate`（`:116`） |
| 构造主体 | 构造 `Principal`（`:169-175`） | 构造 `Principal`（`:137-143`） |
| **成功写审计** | **无** | `log_auth_event`（`:89-96`、`:129-136`） |
| **失败写审计** | **无** | `log_auth_event`（`:106-113`、`:118-125`） |

即：**同一个认证动作，Web 端落 4 类审计事件，CLI 端一条都不落**。这恰好是
`bootstrap/core.py` 想要避免的那类分叉，只是漏在了认证路径上——因为认证逻辑
不在 `bootstrap` 装配的对象里，而是以模块函数形式存在。

**次要差异**：同一个 dev key 构造出的 `Principal` 字段不同——
`deps.py:97-103` 显式带 `scopes=frozenset(ROLE_PERMISSIONS["admin"])`，
`cli.py:160-165` 不带（落到 `principal.py:37` 的默认空集）。
当前 `Principal.has_permission`（`principal.py:40-49`）只读 `role`，所以尚未造成越权；
但两个入口对"同一个主体是谁"的描述已经不一致，日后若让 `has_permission` 参考
`scopes`，CLI 侧会静默失去权限。

**影响**：安全事件的可追溯性在两个入口不对等；换 key 校验实现（加缓存、改哈希算法、
加撤销检查）必须改两处，漏一处即产生一个入口的静默降级。

### Q5：`runtime` 的 7 个 `open_*` 生命周期样板逐字重复

**现象**：7 个存储模块各自实现一遍相同的连接生命周期。

**清单**：`open_thread_store`（`thread_store.py:1046`）、`open_audit_store`（`audit_store.py:307`）、
`open_api_key_store`（`api_key_store.py:272`）、`open_usage_store`（`usage_store.py:367`）、
`open_skill_store`（`skill_store.py:300`）、`open_knowledge_store`（`knowledge_store.py:773`）、
`open_store`（`store.py:25`）。

**逐字重复的结构**：

| 结构 | 出现位置 |
| --- | --- |
| `db_path.parent.mkdir(parents=True, exist_ok=True)` + `ValueError("db_path 不能为 None")` | 全部 7 个 |
| `PRAGMA journal_mode=WAL;` + `PRAGMA busy_timeout=5000;` | `thread_store.py:1081-1084`、`store.py:62-63`、`knowledge_store.py:818-819` |
| `try/except Exception: logger.exception("<X>初始化失败"); raise` | `thread_store.py:1094-1096`、`knowledge_store.py:870-872`、`store.py:69-71` |
| `finally: await conn.close(); logger.info("<X>连接已关闭")` | `thread_store.py:1100-1103`、`store.py:74-78` |
| 每个 store 类各持一把 `asyncio.Lock` | `api_key_store.py:94`、`skill_store.py:79`、`thread_store.py:335` |

**为什么这不是"可以接受的重复"**：项目自己已经确认它是风险点，并为此写了一个专门的
测试文件（当前分支未提交）：

```3:6:tests/runtime/test_open_store_contract.py
WHY 单独成文件：这条契约由 runtime 下六个模块**共同**承担——``open_thread_store`` /
``open_audit_store`` / ``open_api_key_store`` / ``open_usage_store`` /
``open_skill_store`` / ``open_knowledge_store``。它们各自的业务测试都在自己文件里，
而出问题的是六份实现里**同一处**结构写法，逐文件各写一条只能证明写了六遍。
```

该文件的 docstring 还记录了真实代价：`python main.py cli` 在 `auth_mode=apikey` 且未设
`HARNESS_API_KEY` 时，真正原因只有一句话，日志里却是 5 条"XX 初始化失败"加 5 份重复堆栈，
排查方向被引向数据库。

**既然已经确认是"同一处"，用 6 份实现去满足 1 条契约就不是终点**。

**附带问题**：store 类**自身没有 `open` / `close`**，生命周期只存在于模块级函数里
（检索 `def open_|def close|async def initialize` 在 `*_store.py` 的类中 0 命中）。
后果是 store 的交易行为可以被单测，但"连接是否正确建立与释放"只能通过模块函数测。

### Q6：README 的目录结构与分层描述已与代码脱钩

**现象**：README 是唯一的对外入口文档，其目录树缺一个完整的顶层包。

```540:554:README.md
MyAgentHarness/
├── main.py             # 入口：分发 cli / web 两个子命令
├── config.py           # 统一配置中心（唯一的环境变量解析处）
├── agent/              # 装配层：模型后端、工具、护栏、图构建
├── application/        # 应用服务：会话编排、事件模型、中断编解码
├── interfaces/         # 适配器
│   ├── cli.py          # 命令行交互
│   └── web/            # FastAPI 服务 + 前端页面
├── llm/                # 模型注册表与构造
├── runtime/            # 检查点持久化、会话元数据表与长期存储
└── workspace/          # Agent 的活动边界（文件读写、记忆、技能）

分层约定：`interfaces` → `application` → `agent` / `runtime`，上层依赖下层，下层不反向依赖。
```

**问题 1 —— 缺项**：目录树没有 `bootstrap/`。全仓检索确认，README 中"bootstrap"

## 4. 治理方案

### 方案一：把根级模块纳入契约可校验范围（对应 Q1）

> **实施状态：已实施（2026-09-20）。承载机制与初版设计不同，原因见下节「工具限制（实测）」。**

#### 目标

让根级模块的依赖边界变成**可执行、CI 会拦**的规则，使规则覆盖面从
"6 个包不可越界"扩展为"**全仓无盲区**"。

目标与初版设计一致，改变的只是承载机制——初版打算用 `.importlinter`，实测走不通。

#### 工具限制（实测，决定了机制的选择）

初版方案要把 8 个根级模块写进 `.importlinter` 的 `root_packages` 并新增 5 条契约。
**这条路走不通**，两次尝试各撞一个硬约束（import-linter 2.15 / grimp 3.17 实测）：

| 尝试 | 实际报错 |
| --- | --- |
| 把 `config` 等写进 `root_packages` | `'config' is a module, not a package. root_packages should only contain packages (directories with __init__.py), not individual .py files.` |
| 退一步：`root_packages` 保持 6 个包，改在契约里引用 `config` | `Module 'config' does not exist.` |

即 import-linter **只接受"包"作为分析根**：单文件模块既不能列为分析根，也不能被契约引用。
要让它看见这些模块，唯一办法是把它们移进某个目录包，而这不可接受：

- `config` 被全仓数十处 `from config import ...` 引用，改动是全局的；
- `knowledge_tools` / `web_tools` 的名字是**配置项取值**（`CUSTOM_TOOL_MODULES=web_tools`），
  移进包会变成 `CUSTOM_TOOL_MODULES=plugins.web_tools`，属面向使用者的破坏性变更。

**结论：换机制，不换规则。** 同一份角色表落成 `tests/test_root_module_contract.py`，
由 `uv run pytest` 执行——它与 `lint-imports` 跑在 CI 的同一个 job 里
（`.github/workflows/ci.yml` 的 `Run tests with coverage` 与
`Enforce layered-architecture contracts` 两步），因此"可执行"与"CI 会拦"
这两条性质没有损失。

#### 为什么不是"把 `knowledge_runtime` 搬进 `bootstrap/`"

前一版评估提过这个选项，现予否决，理由：

`knowledge_runtime` 存在的**唯一**理由是被自定义工具插件取用
（`knowledge_runtime.py:3-7`：扩展点只把 `config` 交给工具模块，没有注入依赖的通道）。
而 `knowledge_tools.py:22` 正是这样的插件。若把它搬进 `bootstrap/`，就会得到
**插件 → 装配层** 的依赖：一个运行期被动态加载进 Agent 的第三方式模块，
反过来依赖应用的组装点。这比"根级模块不在契约内"更糟——契约 6 的意图
（装配层只能被接口层调用）会被从插件侧绕开。

**保留在根级、但纳入契约**，才是既保住插件可达性、又堵住盲区的做法。

#### 适用范围（实际实施）

| 文件 | 变更 |
| --- | --- |
| `tests/test_root_module_contract.py` | **新增**：角色表 + 4 类断言（含反方向那一类） |
| `.importlinter` | 尾部增加**反向指路注释**（ASCII），说明根级模块为何不在此文件内、去哪找；6 条既有契约零改动 |
| 根级 8 个模块 | **零改动**——本次只让规则可见，不碰代码 |

#### 实施步骤（实际实施）

**步骤 1 —— 角色表**：以 `_BOUNDARIES: dict[str, frozenset[str]]` 声明每个根级模块
允许依赖的仓库内顶层模块。角色划分与初版设计完全相同：

| 角色 | 模块 | 允许的仓库内依赖 | 依据 |
| --- | --- | --- | --- |
| 中立叶子 | `config` / `text_utils` / `thread_utils` / `web_safety` | **空集**，不得依赖仓库内任何模块 | 它们存在的理由就是"最底层、跨层共用"（`text_utils.py:3-6`、`thread_utils.py:3-8`）。一旦任一 import 了上层，下沉的理由消失，且会立刻构成循环 |
| 服务句柄 | `knowledge_runtime` | `application` / `llm` / `runtime` / `config` | 装配与拆除的所有权在 `bootstrap`（`bootstrap/core.py:88`、`:180-183`），取用方是知识库插件（`knowledge_tools.py:22`） |
| 工具插件 | `web_tools` / `knowledge_tools` | `agent`（注册 SPI）、`config`、`web_safety`、`knowledge_runtime` | 插件被动态加载进 Agent 进程，只能依赖注册 SPI、中立模块与自己的服务句柄；直接摸 `application` / `runtime` 会绕过应用层的归属校验、审计与限流，而插件是最暴露于提示词注入的那部分代码 |
| 入口分发 | `main` | `application` / `config` / `interfaces` | `main.py` 只做"解析参数 → 分发"。装配必须经 `interfaces` → `bootstrap`，否则 P1/P3 式的"入口自行装配"会从 `main.py` 长回来 |

**步骤 2 —— 四类断言**。初版设计的 5 条契约全部落到这四类里，一条不丢：

| 初版契约 | 现在由谁承担 |
| --- | --- |
| 7 中立叶子不依赖仓库内任何模块 | 用例 1（`_BOUNDARIES` 里四个空集条目） |
| 8 服务句柄不得被业务层与其它插件**直接**依赖 | **用例 4**（反方向：全量扫描分层包与根级模块，只放行 `bootstrap` 与 `knowledge_tools`） |
| 9 服务句柄自身不直接依赖 `agent` / `interfaces` / `bootstrap` | 用例 1（`knowledge_runtime` 的角色集合里没有这三项） |
| 10 工具插件不直接依赖 `application` / `runtime` / `interfaces` / `bootstrap` / `llm` | 用例 1（两个插件的角色集合里没有这五项） |
| 11 `main` 不直接依赖 `agent` / `runtime` / `llm` / `bootstrap` | 用例 1（`main` 的角色集合里没有这四项） |

四条断言分别是：

1. `test_root_module_imports_stay_within_its_role[...]`（按模块参数化）：实际依赖集合
   必须**等于**角色表声明的集合。
2. 同上用例的第二条断言：角色表里**过时**的条目也必须清理，否则表格会退化成
   "历史记录"，下一个读表的人会以为那条边还在。
3. `test_every_root_module_declares_a_role`：仓库根新增的任何 `.py` 都必须登记角色。
   这条守的是"**盲区不再新增**"——新增根级文件不需要修改任何既有代码，
   不会有任何东西提醒作者它还缺一条约束。
4. `test_service_handle_is_reached_only_by_its_legitimate_callers`：扫描六个分层包与
   八个根级模块，除 `bootstrap` 与 `knowledge_tools` 外不允许任何模块直接依赖服务句柄。

**步骤 3 —— 用 AST 而不是 `sys.modules`**：静态解析与 `.importlinter` 的口径一致，
且覆盖 `if TYPE_CHECKING:` 块与函数内的延迟导入。这不是洁癖：历史上 13 处
`interfaces → runtime` 越界正是靠延迟导入藏住的，而下面的注入验证里有两类正是这种形态。

顺带一个必须澄清的点：**注释中出现的模块名不会被误判**（AST 不含注释节点）。
对本仓库尤其重要——这些模块的 docstring 与注释里大量讨论彼此的依赖关系，
若按文本匹配实现，`interfaces/web/knowledge_routes.py` 与 `interfaces/web/app.py`
里那两句提到 `knowledge_runtime` 的注释会立刻变成误报。

**步骤 4 —— `.importlinter` 留反向指路注释**：写明根级模块为何不在该文件内、去哪找。
没有这条注释，下一个发现"少了一条规则"的人会把模块加进 `root_packages`，
然后撞上前面那两个报错——同一段弯路会被反复探索。

#### 实施后的可校验范围

| 项 | 实施前 | 实施后 |
| --- | --- | --- |
| 契约管不到的顶层模块数 | 8 | **0** |
| `.importlinter` 契约数 | 6 条 | 6 条（不变；根级模块由契约测试承担） |
| 插件模块的依赖面 | 无约束 | 由角色表固定 |
| `main.py` 自行装配 | 可发生且无人拦 | 被用例 1 拦住 |
| 除装配层与插件外取用服务句柄 | 可发生且无人拦 | 被用例 4 拦住 |
| 新增根级模块 | 静默无约束 | 必须登记角色，否则 CI 红 |

#### 预期效果（已实测，不是预测）

### 方案二：消除规则的两份复制（对应 Q2）

> **实施状态：已实施（2026-09-20）。步骤 2 与初版设计不同**——不是复用 `truncate`，
> 而是新增 `truncate_with_notice`。照初版做会让两处工具输出**改变行为**，见下。

#### 目标

把"复制"改回"委托"，使同一条规则在全仓只有一份判断逻辑。

#### 适用范围（实际实施）

| 文件 | 变更 |
| --- | --- |
| `runtime/usage_store.py` | `_validate_thread_id` 改为委托；新增 `from thread_utils import normalize_thread_id` |
| `text_utils.py` | **新增** `truncate_with_notice`；`truncate` 补 `text` 类型校验 |
| `web_tools.py` | `_truncate` 改为委托（签名与文案逐字不变） |
| `knowledge_tools.py` | `_truncate` 改为委托（签名与文案逐字不变） |
| `tests/test_root_module_contract.py` | 两个插件的角色表补 `text_utils`（见下「契约拦住了这次改动」） |
| `tests/test_text_utils.py` | **新增**：两个截断口径各自的边界、以及「两者不能合并」的断言。该模块此前只被间接覆盖，而间接覆盖发现不了「某一侧的上限悄悄失效」 |

#### 实施步骤

**步骤 1 —— 会话 ID 校验改委托**：方法体改为 `return normalize_thread_id(thread_id)`，
import 照 `thread_store.py:29-30` 的既有写法。保留同名静态方法作为调用点的稳定名字，
不改调用方。

**步骤 2 —— 截断：新增 `truncate_with_notice`，而不是复用 `truncate`**（与初版设计不同）。

初版设计写的是"判断逻辑统一走 `text_utils.truncate`"。**核对后否掉**：两者的长度口径相反——

| | `truncate(text, limit)`（已有） | `truncate_with_notice(text, limit, notice)`（本次新增） |
| --- | --- | --- |
| 面向 | 展示（会话标题） | 工具输出（会被模型当输入读） |
| 省略号 / 提示语 | 省略号**占一个字符** | 提示语**独立追加** |
| 结果总长 | **不超过** `limit` | **可以超过** `limit` |
| 现有调用方 | `build_title` | `web_tools` 抓取正文、`knowledge_tools` 检索片段 |

直接复用 `truncate` 会让两处工具输出悄悄变行为（保留字符数少 1、且提示语样式被换掉），
而这两处各有断言钉着（`tests/test_web_tools.py:443`、`tests/test_knowledge_tools.py:142`）。
**新增一个函数、共用那句 `len(text) <= limit` 判断**，才是"收敛怎么算、不收敛怎么说"。

需要共用的不是口径，而是**判断**：未超限就原样返回，超限才追加提示语。
各写一份最可能出现的偏差是"提示语无条件追加"——于是没被截断的结果也自称被截断了。

**步骤 3 —— 顺带核对硬编码 `128`**：实测 `runtime/` 下与会话 ID 相关的 `128`
只有 `usage_store.py:331` 一处。同文件的 `MAX_MODEL_CHARS`（`:26`）与
`_MAX_OWNER_CHARS`（`:27`）是**另外两条规则**（模型名、所有者 ID 的长度上限），
不在本次范围。

#### 契约拦住了这次改动（方案一的第一次真实回报）

给两个插件加 `from text_utils import ...` 之后，方案一建立的根级模块契约立刻失败：

```
AssertionError: knowledge_tools.py 依赖了 ['text_utils']，
超出它声明的角色范围 ['agent', 'config', 'knowledge_runtime']。
```

这不是误报，而是**要求作者对新增的那条边表态**——正是它存在的目的。评估后放宽：
插件角色的理由是"只能依赖注册 SPI、中立模块与自己的服务句柄"，而 `text_utils`
正是中立叶子（自身零仓库内依赖），与允许集里已有的 `config` / `web_safety` 同类。
于是更新角色表，并在注释里写明这次放宽的理由与日期——**放宽是被记录的动作，
不是被忽略的事实**。

#### 预期效果（实施后实测）

| 项 | 实施前 | 实施后 |
| --- | --- | --- |
| 会话 ID 规则的判断实现 | 2 份 | 1 份（`thread_utils`），`usage_store` 为委托 |
| 截断判断逻辑 | 3 份 | 1 份（`text_utils.truncate_with_notice`） |
| 修改会话 ID 上限需要动的文件 | 2 个 | 1 个 |
| 工具输出的提示语 | 两种措辞（各一份） | **两种措辞逐字不变**（有意保留） |

#### 风险

| 风险 | 概率 | 缓解 |

### 方案三：认证校验收敛为共享实现（对应 Q3）

#### 目标

#### 适用范围

- 新增 `application/api_key_auth.py`（或 `application/auth_service.py`，命名以实施时的
  既有命名习惯为准）

与 `Principal`（`application/principal.py`）。放应用层符合既有分层，

**步骤 1 —— 定义共享校验入口**，职责三步：dev key 比对 → 存储校验 → 构造 `Principal`。
审计**不写在校验函数里**（审计是"发生在某次请求里的事"，需要请求上下文）。

这一侧的行为**必须零变更**——它现在是对的。

**步骤 3 —— CLI 侧接入**：`cli._validate_api_key_for_cli` 改为调用共享函数。
CLI 无 HTTP 请求上下文，因此它记的是**进程级审计**：审计记录须带
`source="cli"`，`client_ip` 留空而不是填假值。

**步骤 4 —— 补齐 CLI 的审计写入**。这是本次的**行为变更点**，必须写进实施记录：

| 事件 | 含义 |
| --- | --- |
| `apikey_auth_success` | CLI 取到凭据且校验通过 |
| `apikey_auth_failure` | 凭据无效 / 未配置 |

**步骤 5 —— `Principal` 字段对齐**：统一由共享函数构造，`scopes` 在两端一致
（按 `ROLE_PERMISSIONS` 填充），消除 `cli.py:160-165` 与 `deps.py:97-103` 的差异。

### 方案五：`open_*` 样板收敛为公共 helper（对应 Q5）

> **实施前现状核查（2026-09-20）**：本方案的部分前置工作已由提交 `fdcec20`
> （"六个存储的初始化失败不再吞掉主体异常"）完成，核查结论与两处新发现见本节末尾
> 「实施前发现的现状」。那批修复先单独提交，正是为了让本方案的 diff 只包含
> "纯结构收敛"——否则一次改动会同时含"修一个真缺陷"与"重写六处函数体"，出问题无法对分。

#### 目标

把 7 份逐字重复的连接生命周期收敛为 1 份实现，且**保留**既有契约测试所守的性质。

#### 适用范围

- 新增 `runtime/sqlite_open.py`（命名以实施时的既有习惯为准）
- 改 7 个 `open_*` 改为调用它
- `tests/runtime/test_open_store_contract.py` 保持不动——它是本次重构的验收工具

#### 实施步骤

**步骤 1 —— 提炼公共上下文管理器**，职责固定为：

1. 显式校验 `db_path` 非 `None`（`ValueError`）
2. 建父目录
3. 建立 `aiosqlite` 连接并施加 PRAGMA（WAL + busy_timeout）
4. 建表（由调用方传入的 `setup` 回调完成）
5. `yield` 已构造的 store（由调用方传入的 `build` 回调完成）
6. `finally` 关连接 + 记日志
7. 初始化失败时记"XX 初始化失败"+ 原样抛出

**步骤 2 —— 关键约束：`yield` 必须落在捕获初始化异常的 `try` 之外**。
这正是 `tests/runtime/test_open_store_contract.py:8-12` 记录的缺陷：
`yield` 若在 `try` 里，`async with` 主体抛出的异常会被误记成"初始化失败"，
于是"真正原因只有一句话，日志里却是 5 条初始化失败加 5 份重复堆栈"。
抽象成 helper 后这条约束**只需实现一次**，且由既有测试继续守住。

**步骤 3 —— 逐个迁移，一次一个模块**（7 个模块即 7 次提交粒度）。
每迁移一个，跑该模块自己的测试 + 契约测试，再迁下一个。
**不一次性改完**：契约测试会同时覆盖 7 个实现，全量替换时一旦失败，
无法定位是 helper 的问题还是某个模块的差异。

**步骤 4 —— 保留差异点**：`open_knowledge_store` 多出 `dims` / `model` /
`vector_enabled` 三个参数，且要加载 `vec0` 扩展。helper 只固化"生命周期"，
扩展加载与参数校验仍留在该模块内。**不要为了整齐而把知识库塞进同一签名**——
它的连接建立方式（加载式扩展）与其余 6 个本质不同。

#### 预期效果

| 项 | 实施前 | 实施后 |
| --- | --- | --- |
| 生命周期实现份数 | 7 | 1（helper）+ 7 处调用 |
| "`yield` 必须在 try 外"的实现点 | 7 | 1 |
| 新增一个 store 需要的样板 | 约 40 行 | 约 10 行（回调 + 类） |
| 契约测试覆盖的 `open_*` 数 | 6 | 仍 6（保持不变即通过） |

#### 风险

| 风险 | 概率 | 缓解 |
| --- | --- | --- |
| 迁移中破坏"初始化失败仍要留记录"的性质 | 中 | 契约测试 `test_real_initialization_failure_is_still_reported` 专门守这条，逐个迁移时必然执行 |
| PRAGMA 差异（如某模块需要额外 PRAGMA）被抹平 | 低 | helper 接受额外 PRAGMA 列表参数；实施前先逐个 diff 7 个 `open_*` 的 PRAGMA 集合 |
| 单次大改导致定位困难 | 中 | 步骤 3 已要求逐个迁移 |

#### 验收标准

1. `pytest tests/runtime/` 全量通过，含 `test_open_store_contract.py` 的 12 条断言
2. 7 个 `open_*` 的公开签名与行为不变（既有测试不改）
3. `runtime/` 内 "初始化失败" 日志文案的产生点只有 1 处
4. `python main.py cli` 在 `auth_mode=apikey` 且未设 `HARNESS_API_KEY` 时，
   日志只有 1 条初始化相关记录（复现 Q5 记载的原始故障场景）

#### 实施前发现的现状（2026-09-20 核查未提交改动）

**已由 `fdcec20` 完成的部分——"异常归因"修复，但每个 store 各修一遍**：

六个 `open_*`（thread / audit / api_key / usage / skill / knowledge）的改动是同**一件事**：
把 `yield` 移出「捕获初始化异常」的 `try`，并把 `conn` 改为可空、`finally` 判空后关闭。
配套新增了 `tests/runtime/test_open_store_contract.py` 用两条断言把它钉住。

也就是说：**原始缺陷（主体异常被误记为"初始化失败"）已经修好**，
但修法是"同一处结构写六遍"——而现在它变成了**六份带注释的同一处结构**：

> 实测：`只把初始化包在捕获里` 这段 5 行 WHY 注释，逐字出现在
> `runtime/` 下 6 个文件里（`search_content` 命中 6 个文件）。

修一次缺陷、重复多一份——这是本方案最直接的论据，比 Q5 当初的记载更有力。

**因此方案五的核心部分一行未做**，且收敛后这 6 段注释只需存在一处。

**新发现 1：契约测试的覆盖边界正好漏掉唯一不达标的实现**。

`test_open_store_contract.py` 的 `_OPENERS` 列了 6 个 opener，**没有 `open_store`**
（长期记忆，`runtime/store.py:25`）。而它恰好是唯一不满足第二条断言
（真·初始化失败要留下"初始化失败"记录）的实现——实测：把库路径占成目录后，

```
raised: OperationalError: unable to open database file
（日志里没有任何"初始化失败"记录）
```

原因是它的 `aiosqlite.connect` 与两个 PRAGMA 都在任何 `except` 之外。
契约的覆盖边界与"唯一不达标的那个"重合了——无论当初是否刻意，
这正是 Q1 说的那类盲区：**看起来被覆盖了**。

处理方式二选一，建议在方案五里一并决定：
（a）修好 `open_store` 的归因，并把它加进 `_OPENERS`（收敛成公共 helper 后它自然满足）；
（b）明确记录"长期记忆存储不适用该契约"及其理由。

**新发现 2：`open_store` 与其余 6 个的差异不止这一点**——它多一个
`isolation_level=None`（事务边界由 `AsyncSqliteStore` 自己管），
且 `setup()` 是 `await store.setup()` 而不是 `executescript(_SCHEMA)`。
这与步骤 4「保留差异点」一致：helper 只固化生命周期，这两处留在调用方。

**顺序（已执行）**：先以 `fdcec20` 单独提交那批"异常归因"修复，再做本方案。理由：本方案要
重写这 6 个函数体，叠在未提交的修复上会让一次 diff 同时包含"修一个真缺陷"与"纯结构收敛"，
出问题时无法对分，评审也无法按性质分开看。现在基线干净，逐模块迁移的每一步都能单独回退。

**步骤 4 —— 页脚承诺改为如实描述**（实施中发现）：该页脚原文承诺
"所有位置引用格式为 `文件:行号`，与源文件一致"。第 3 章「关键文件职责」表的行号
已普遍滞后（实测三例）：

| 表中标注 | 实测 | 偏移 |
| --- | --- | --- |
| `main() main.py:79` | `main.py:137` | +58 |
| `open_thread_store() :360` | `runtime/thread_store.py:1046` | +686 |
| `ThreadMetaStore :76` | `runtime/thread_store.py:321` | +245 |

因此把承诺改写为"**符号名有效，请按名检索、不要按行号跳转**"，
并把行号复核登记为方案七（不塞进本次：逐行核对是另一件事，且它需要每个符号单独取证）。

### 方案七：复核 `architecture.html` 的行号引用（对应 Q7）

#### 目标

把"所有位置引用与源文件一致"从**一句无法自证的承诺**，变成**可以复核的事实**。

#### 为什么与方案六分开

方案六按文档单元修（目录树、分层描述、页脚承诺），一次替换即完成；
方案七要逐符号取证（每个引用都要在源码里定位一次），是另一类工作。
两者混在一起会让方案六无法在小改动后收尾——这正是 Q6 当初积累成问题的路径。

#### 适用范围

- `docs/overview/architecture.html` 全篇的 `文件:行号` 引用
- 不改代码

#### 实施步骤

1. **建一张清单**：把全篇 `文件:行号` 出现处抽出，标注所属章节。
   优先第 3 章「关键文件职责」表（已知 13 行全部滞后）。
2. **逐条取证**：对每个引用，在源码里定位该符号的真实行号，记录"标注值 / 实测值"。
3. **按偏移量分类**：若同一文件的偏移是**常量**（说明是某次纯插入导致的整体平移），
   可按偏移批量修正；若偏移不一致，说明其间发生过结构性改动，必须逐条核对。
4. **修正后加一道防线**：在 CI 增加一条把该表与源码比对的检查，
   或在页脚声明"行号以版本为准"。**不设防线的修正会再次腐烂**——
   这就是它第一次腐烂的原因。

#### 预期效果

| 项 | 实施前 | 实施后 |
| --- | --- | --- |
| 可复核的引用 | 0 | 第 3 章表格全部 |
| 读者按行号跳转的成功率 | 低（偏移 58–686 行） | 有效，或页脚已明确声明不以行号为准 |

#### 风险

| 风险 | 概率 | 缓解 |
| --- | --- | --- |
| 修正完成即开始第二次腐烂 | 高 | 步骤 4 的防线是必要项，不是可选优化 |
| 逐符号核对成本被低估 | 中 | 先做第 3 章表格（读者最常跳转处），其余章节按引用密度排序 |

#### 验收标准

1. 第 3 章「关键文件职责」表的每个引用都能跳转到正确符号
2. 存在一条可执行检查或明确声明，使该表不会无声腐烂
