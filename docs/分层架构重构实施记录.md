## 3. 关键节点与遇到的问题

### KN-1 Windows 环境下的 GBK 编码问题

**现象**：首次运行 `uv run lint-imports` 报错：

```text
'gbk' codec can't decode byte 0x80 in position 31: illegal multibyte sequence
```

**原因**：Windows 下 Python 默认以 locale 编码（GBK）读取 `.importlinter`，而配置文件含中文注释（UTF-8）。

**处理**：运行前设置 `PYTHONUTF8=1`。

```powershell
$env:PYTHONUTF8=1; uv run lint-imports
```

**说明**：Python 3.15 起 UTF-8 模式将默认开启，此问题会自动消失。项目当前要求 `requires-python = ">=3.14"`。

### KN-2 `root_packages` 不接受单文件模块

**现象**：配置中加入 `config` 与 `text_utils` 后报错：

```text
'config' is a module, not a package. root_packages should only contain packages
(directories with __init__.py), not individual .py files.
```

**处理**：从 `root_packages` 中移除 `config` 与 `text_utils`，仅保留 6 个包目录。

### KN-3 `forbidden` 契约默认包含间接依赖

**现象**：首次运行契约 1 报 BROKEN，但列出的全部是间接路径，例如：

```text
- interfaces.cli -> application.run_service (l.28)
  application.run_service -> runtime.audit_store (l.21)
```

**原因**：`forbidden` 契约默认检查传递依赖。而 `interfaces → application → runtime` 是分层设计的正常路径，若一并禁止，该契约会与"application 允许依赖 runtime"自相矛盾。

**处理**：契约 1 与契约 6 增加 `allow_indirect_imports = True`，只约束直接导入。

### KN-4 方案调整：新增 `application/ports.py` 与 `application/thread_id.py`

**背景**：方案一的验收标准要求"`interfaces/` 目录下不存在任何 `from runtime` 语句"，但实施中发现两类残留：

1. `interfaces/web/auth.py` 有 4 处 runtime 类型注解（`APIKeyStore` 等）
2. `interfaces/web/routes.py` 有 1 处 runtime 函数导入（`normalize_thread_id`）

**调整内容**：

- 新增 `application/ports.py`：用 `typing.Protocol` 描述接口层所需能力（审计、API Key、device flow、限流）。`runtime` 的实现类因结构化子类型自动满足协议，无需显式继承，因此不产生新的耦合。
- 新增 `application/thread_id.py`：作为门面重新导出 `normalize_thread_id`。该函数的实现留在 `runtime` 是因为存储层也要用它做入参校验，迁移到 `application` 会让 `runtime` 反向依赖 `application`。

**偏离说明**：这两项不在原方案的步骤清单中，属于实施过程中发现的必要补充。原方案只考虑了「装配职责」带来的跨层依赖，未识别「类型注解」与「共享校验函数」这两条路径。

### KN-5 方案调整：装配方向由 `bootstrap → interfaces` 改为 `interfaces → bootstrap`

**背景**：原方案一的目标态依赖图是 `bootstrap → interfaces`，即在 `bootstrap` 中构造 `AppContext` 后传给 `create_app(context)`。这要求启动方式改为：

```python
async with build_app_context(config) as context:
    app = create_app(context)
    server = uvicorn.Server(uvicorn.Config(app, ...))
    await server.serve()
```

**问题**：原方案自己的「风险」条目已指出，这会改变 `uvicorn.run()` 的信号处理行为（`uvicorn.run` 内部自行注册 SIGINT/SIGTERM 处理器）。

**调整**：改为在 `interfaces` 侧的 `lifespan` 内调用 `build_app_context`，保留 `uvicorn.run(app, ...)` 不变。相应地，`.importlinter` 契约 6 从"bootstrap 不得被任何层依赖"调整为"bootstrap 不得被 application / agent / llm / runtime 依赖"，显式允许 interfaces 依赖它。

**取舍**：`interfaces` 因此保留了对 `bootstrap` 的依赖（装配入口职责），但换来了启动路径零行为变更。这一取舍需要后续评估，见遗留问题 L-4。

### KN-6 CLI 残留 TYPE_CHECKING 导入

**现象**：契约 1 报出 `interfaces.cli -> runtime.api_key_store (l.29)`，经查是 `if TYPE_CHECKING:` 块内的类型注解导入。

**处理**：改用 `application.ports.APIKeyRepository`，两处函数签名的 `"APIKeyStore | None"` 同步替换。

## 7. 后续建议

### 7.1 优先级 P0

1. **补做端到端功能回归**（对应 L-1）
   - 启动应用，用真实 Authentik 实例走通登录、登出、API Key 管理、CLI Device Flow 四条主路径
   - 重点验证：拆分为子包后 `router` 挂载与中间件顺序是否与原实现完全一致

### 7.2 优先级 P1

2. **接入 CI / pre-commit**（对应 L-3）
   - 将 `uv run lint-imports` 加入提交前钩子，并显式设置 `PYTHONUTF8=1`
   - 这是把"规则"变成"约束"的关键一步，否则契约会随时间退化

3. **同步更新方案文档的目标态图**（对应 L-6）
   - 把 `bootstrap` 的实际位置（被 `interfaces` 依赖）更新到 `分层架构评估与重构方案.md` 第 10.2 节

### 7.3 优先级 P2

4. **消除 `PYTHONUTF8` 依赖**（对应 L-2）
   - 方案 A：把 `.importlinter` 的注释改为英文
   - 方案 B：在项目 README 中明确记录该前置条件

5. **评估 `normalize_thread_id` 的真正归属**（对应 L-5）
   - 若确认它属于领域规则，可下沉到与 `text_utils.py` 同级的中立模块，届时 `application/thread_id.py` 门面即可删除

6. **评估 CLI 装配上移到 `main.py`**（对应 L-4）
   - 让 `interfaces` 完全不含装配知识，`main.py` 负责组装后再调用 `run_cli(context)`
   - 代价是需要调整 CLI 的入口签名，收益是接口层职责更纯粹

7. **清理未使用的私有函数**（对应 L-7）
   - `device_flow.py` 的 `_device_flow_expires_at` 确认无用途后删除
