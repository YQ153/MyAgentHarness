1. 项目定位与技术栈

MyAgentHarness 是一个通用任务 Agent 的骨架工程。它不是某个垂直业务机器人， 而是一套「把大模型变成能干活的助手」所需的完整基础设施：受限于工作区的文件读写、 任务规划与待办、子任务委派、高危操作的人工审批、会话持久化与长期记忆。

工程的核心特征是 双形态同内核：命令行（CLI）与 Web 服务共享同一套 应用服务与 Agent 内核，两者的差异被严格压缩在「事件怎么渲染」和「人工决策从哪来」 两个适配点上。

2. 整体架构设计

会话根：一条会话的「文件根」

每个会话有且只有一个文件根：Agent 的文件工具、沙箱挂载根、附件目录、 技能来源与知识库索引全部以它为准。根只有两种来源，没有第三种：

  • 用户绑定的工作空间——新建会话时从宿主机上任意目录里挑一个 （不限制路径范围，这是产品规则）。同一个工作空间可以承载多条会话：它们的文件、附件与索引 都落在同一个项目目录里。
  • 会话专属目录——没选工作空间的会话，由应用在 SESSIONS_ROOT （默认 <数据目录>/sessions，见 resolved_sessions_root config.py:1318）下按会话 ID 自动创建独立子目录（session_dir config.py:1353），只有它自己用。WHY 要跟着数据目录走：会话的检查点、审计与 用量都在数据目录里，「备份/搬迁只需要搬一个目录」才成立。

已有会话的根存在 thread_meta.workspace；thread_meta.workspace_bound 记录它当初是「用户选的」还是「应用建的」——界面靠它决定文案（「工作空间：…」还是 「会话专属目录：…」）。WHY 单独存这一列而不从路径推断：用户完全可以把工作空间选在 sessions 目录里面。

锁定：产生第一条交互之后不可更换

锁定发生在「这条会话第一次真正跑起来」的那一刻 登记与锁定是同一条 UPSERT（ThreadMetaStore.record_turn runtime/thread_store.py:515），而它只在会话的根还为空时才写入（SQL 里的 CASE 分支）。WHY 不放在更早的建会话接口里：那个接口只发号、不落库（会话在 首条消息时才诞生），提前写入会凭空造出一种「有根但没有内容」的记录。
锁定之后不再接受改值 后续请求如果给出不同的工作空间，直接 409 拒绝 （SessionRootLockedError）。WHY 不「以请求为准」：这条会话的文件、技能视图、 附件目录与索引都已经锚在旧根上，中途换根会把半条会话留在旧目录、半条写到新目录， 而两侧都不会报错。要换项目请新建会话。
还没有根时如实说「还没有」——但仅限「连会话 ID 都没有」 草稿态（连 ID 都还没申请）下的面板请求既没有可派生的专属目录，也没有用户指定的工作空间， 此时返回 409（SessionRootNotReadyError）并说明原因，而不是悄悄退到 某个默认目录：那会让用户在「以为在看自己的项目」的面板里看到别处的文件，而两边都不报错。
「未绑定工作空间的新会话」不属于这一种：它的 ID 在首次发送前 就已经发出，专属目录由该 ID 派生得出，因此解析直接给出那个目录（并与第一轮交互登记的根一致）。 WHY 这点值得单列：首条消息的附件构造与运行前的根解析都必须赶在会话登记之前完成，一旦这里报 「还没有根」，不选工作空间这条正常路径就会被自己的提示（「请先发出第一条 消息」）挡在门外——照着提示再发一次，结果一模一样。
解析出来的根一定可用（专属目录按需创建） SessionRegistry.resolve 返回之前会保证那个目录存在：应用自己建的 专属目录按需建出来；用户选定的目录不见了则报 409 （SessionRootUnavailableError），并提示「恢复该目录，或删除这条会话」。 WHY 收在这一处：下游（Agent 装配、Backend、附件索引、文件面板）全都假定根存在，而专属目录 在第一次真正需要落文件之前并不存在——少了这一步，「打开一条还没发过消息的会话」会在构造 Backend 时撞上它那条「根必须是已存在的目录」的断言，用户点开自己的会话看到的是一个与他的 操作毫无关系的 500（NotADirectoryError 还是 OSError， 连 except RuntimeError 的兜底都接不住）。 WHY 不替用户重建：那是他选定的项目目录，建一个同名空目录会让「我的项目被清空了」看起来成真。

长期记忆：一份全局的，一份随工作区走的

记忆分两层，来源不同、生效范围也不同：全局那份由 MEMORY_FILE 指定（人工维护、跨会话共享的偏好与约定），工作区 那份是各会话根下的 AGENTS.md（项目自己的说明）。两者合起来由 SessionRoot.memory_plan（config.py:1716）给出：来源列表 与为它们准备的挂载点。

全局记忆为什么要「挂载」而不是「要求它放在工作区里」 Agent 的文件根是本会话的工作区，而全局记忆按定义就在任何工作区之外。deepagents 的 memory 参数只收虚拟路径，而它对读不到的来源是静默跳过的 （只留一行 WARNING）——于是「配了全局记忆的实例里所有会话都少一条记忆」这件事不会以任何 错误的形式出现，用户看到的是「我明明写了约定，Agent 不照做」。做法是把那个文件作为 只读挂载点接进虚拟文件系统（/global/AGENTS.md，见 agent/readonly_mount.py）：Agent 读得到、引用得到，但写不动—— 「人工维护」这条承诺因此有硬保证，而不是靠提示语叮嘱。 WHY 不复制/软链进根：那会让文件出现第二份真相，人工改了源文件而副本没变时，Agent 读到旧 内容且不报错。WHY 不放行任意绝对路径：那等于拆掉「Agent 能碰宿主哪片目录」这条边界。
两处记忆只留一个来源 MEMORY_FILE 一旦配置，工作区自带的 AGENTS.md 就不再 作为来源（它存在时记一行 INFO）。WHY：deepagents 只是把来源一起塞进提示，两处说法冲突时 没有任何优先级依据，用户很难理解「我改的是全局那份，Agent 却不照做」。同理，配了全局记忆 但文件不在时不静默回落到工作区那份——那会让用户以为生效的是 A，实际是 B。

应用数据目录：工作区里的 .harness/

技能库、技能视图、工具输出留存与知识库索引统一住在工作区内的 <根>/.harness/{skills, skills-active, tool-outputs, knowledge.db} （SessionRoot.storage_dir，config.py:1761）。

为什么放在工作区内：这些内容属于这个项目 技能是「这个项目常用的套路」，留存是「这个项目的运行记录」，知识库索引的对象就是工作区里的 文档——它们跟着项目走，换机器或换工作空间之后行为才一致；放在数据目录下则表现为「换个工作 空间就什么都要重配」，而用户不知道发生了什么。
代价是明确的：工作区可能是用户的仓库，所以这里会多出一个 .harness/（2026-09-21 曾为同样理由把它搬到数据目录，本次按「内容应随项目走」 搬回）。配套两条约束：文件面板不列出它；要在版本控制里忽略它，需要用户 自己把 .harness/ 写进 .gitignore（应用不替用户改仓库里的文件）。
为什么仍然要挂回来：内容虽然就在工作区内，但对 Agent 只经固定虚拟路径 暴露（/skills、/.skills-active、/_tool_outputs）—— 由 agent/readonly_mount.py 的目录挂载提供，写一律拒绝。额外 多挂一条 /.harness/ 是为了堵住绕行口：没有它，Agent 换一条路径 （/.harness/skills/…）就能写到同一批文件，因为 virtual_mode 只拦 越界、不拦写。
为什么按根派生、不按会话分：同一个工作空间可能承载多条会话，而「这里装了 什么技能」本来就该共享（启停状态也是全应用一份）；按会话分会让第二条会话看不到第一条装好的 技能——那正是「技能库」这个概念要消除的重复。
迁移：技能包会搬，派生物不搬 该根第一次被使用时，两代旧位置里的技能包与留存会被搬进 .harness/：① <数据目录>/roots/<根标识>/（2026-09-21～ 09-22 的布局）；② 更早的 <根>/skills。技能是用户放进来的东西，静默丢掉 等于让它凭空消失。skills-active 是派生物（重建即可，且必须与当前启停状态一致）， 不迁移。
只认形状、不认名字：skills 是很常见的目录名，因此只有当它里面 确实存在含 SKILL.md 的子目录时才迁移——「打开项目后被应用搬走目录」是历史上 真实发生过的事故。
例外：显式配置了 SKILL_DIRS 时技能库就是那些 目录——此时既不建我们那份，更不能把 <根>/skills 当旧位置搬走（那可能是 用户自己配进去的路径，搬走会让配置里的路径凭空消失）。

怎么挑：两种入口

入口端点适用与限制
系统文件夹选择对话框 POST /api/workspaces/pick 原生弹窗、最省事。窗口出现在运行服务端的那台机器上——浏览器页面 拿不到宿主的绝对路径（<input webkitdirectory> 只给相对名， File System Access API 只给一个 handle），要拿到 D:\projects\my-app 这种取值只能由服务端进程在自己的桌面上弹。因此容器 / 无桌面 / 浏览器与服务端分离 的部署会得到 501。
网页内逐级浏览（也可直接粘贴路径） GET /api/workspaces/dirs 只列目录、一次一层，从盘符（Windows）或 /（POSIX）出发。任何部署都能用， 是上面那条路走不通时的替代。

两条路都没有位置限制：工作空间允许用户任意选择（这是产品规则），服务端 不再过滤位置，唯一的门槛是权限本身（file:read）——能选任意目录，就意味着能读 任意目录。

实现落在 runtime/folder_picker.py（宿主侧进程控制，与 sandbox 同类），经应用层的 choose_workspace_folder（application/session_registry.py:217） 与 list_directories（application/session_registry.py:151）暴露给路由： interfaces 按分层契约不能直接依赖 runtime。弹窗的失败各自映射到 不同状态码——环境不支持 501（该换入口）、已有弹窗 409（该重试）、 超时 504（窗口可能还留在屏幕上）；用户取消是 200 cancelled=true （他什么都没做错）。

解析与装配集中在 SessionRegistry（application/session_registry.py:265）： 前者按上述规则算出「这次请求用哪个根」，后者按根装配文件面板 / 附件 / 技能视图 / 知识库四类 服务并缓存（同一个根只装配一份）。WHY 两者必须挨着：分开取用迟早拼出「面板指向 A、附件写到 B」 这种组合，而那不会报错。

4. 核心组件：配置中心

config.py 是全应用唯一的环境变量解析点，读取优先级为 环境变量 > .env 文件 > 字段默认值（config.py:471）。 选用 pydantic-settings 而非裸 os.getenv，是为了让类型转换、 缺省值与非法值拦截由框架统一处理。

三类字段

  • 模型与 LLM 参数：deepseek_*、llm_temperature（限 0–2）、llm_timeout（>0）、llm_max_retries（>=0）。
  • 运行时路径：sessions_root（未绑定工作空间的会话，其专属目录的父目录，留空按 <数据目录>/sessions 派生）、memory_file（全局长期记忆，留空即改用各会话根下的 AGENTS.md）、db_path、skill_dirs（留空即按各会话根派生）。
  • 安全与护栏：execution_mode、shell_timeout、shell_max_output_bytes、max_model_calls_per_run、recursion_limit。

路径处理的两个关键约定

这两条都落在 SessionRoot（config.py:1620）而不是 AppConfig 上。WHY：工作区在会话级可选之后，凡是由它派生的东西 （技能目录、虚拟路径映射、工作区自带的记忆文件）都必须跟着某一个具体工作区算。 把这些方法留在配置对象上并各加一个 root 参数，任何一处漏传都会静默 退回启动默认值——而症状是文件落进了别人的项目。收进一个必须显式获得的对象里，漏了就是 AttributeError。

唯一的例外是全局长期记忆：它按定义不跟着任何工作区走，因此它的路径来自 AppConfig.memory_file——但它进入 Agent 的方式（只读挂载）仍然由 SessionRoot 统一给出，免得「来源」与「挂载」两处各算一份而漂开。

1. 路径统一展开为绝对路径 _expand_path（config.py:1089）对 memory_file / db_path 执行 expanduser().resolve()；根目录 在同一位置展开，并额外校验它已存在且是目录。 WHY：Backend 的 root_dir 若为相对路径，进程工作目录一旦变化就会指向不同物理目录； 而工作区若交给 ensure_directories() 去 mkdir， 一个拼错的路径会被「成功」地变成一个空目录。
2. 传给 deepagents 的路径必须是「相对工作区的 POSIX 路径」 skill_source_paths()（config.py:2206）与 memory_plan （config.py:1716）都给出相对本工作区的虚拟路径。唯一的例外是全局长期 记忆：它在工作区之外，走只读挂载（/global/…），因此给出的是挂载点内的 路径而不是工作区内的相对路径。 WHY：虚拟文件系统内部以 / 为根分隔符，且 Backend 的根就是这条会话的文件根； 传宿主机绝对路径（Windows 下还带盘符与反斜杠）永远命中不了。 工作区**之外**的技能目录（内置技能就是这种）不能靠拼接映射，改由 read_only_mounts 挂一个虚拟路径——不挂的话它一个都读不到，且没有任何告警。

skill_sources()（config.py:2167）在技能目录缺失时只记录告警 并跳过该来源，而不报错——技能库属于可选能力，缺失应当降级而非让应用无法启动。

8.2 runtime/store.py：长期记忆

open_store() 以异步上下文的方式提供 langgraph.store.sqlite.aio.AsyncSqliteStore，与检查点共用 DB_PATH 指向的同一个 SQLite 文件。WHY 用 SQLite 实现而不是 InMemoryStore：后者的生命周期与进程一致，重启即失，而文档与 /memories/ 路由承诺的是「跨会话记忆」；而 SQLite 版 Store 由 langgraph-checkpoint-sqlite 附带，本项目已依赖该包，因此是零新增依赖的替换。

两个必须显式设置的 PRAGMA：journal_mode=WAL（库级持久属性，但本模块 不应假设初始化顺序）与 busy_timeout=5000（连接级属性， 缺了它会在与审计 / 用量表并发写入时立刻抛 database is locked，而 Agent 写记忆恰好发生在运行中途）。必须用 AsyncSqliteStore 而非同步版： 图内的文件工具走异步 backend，而该实现的同步接口在事件循环里会直接抛 InvalidStateError。

管理口径 管理接口（application/memory_service.py + GET/DELETE /api/memories） 直接读写同一个 store 实例，命名空间同样按主体收敛，因此面板与 Agent 看到的是同一份数据。 存储层的键是去掉 /memories 挂载点的相对路径 （/notes.md），对外统一还原成 /memories/notes.md。

8.3 runtime/thread_store.py：会话元数据表

检查点表只保存图状态，其 metadata 是 LangGraph 自用字段 （source / step / writes），既没有标题也没有时间戳， 而会话列表恰恰需要这两项。靠反序列化 BLOB 凑列表成本极高（每条会话都要解包 msgpack）， 因此另建一张窄表 thread_meta，与检查点共用同一个 SQLite 文件—— 两者描述的是同一批会话，分库会带来「删了会话却删不掉元数据」的跨库不一致。

                      ELSE thread_meta.title END

一次往返同时完成「刷新活动时间 + 累加轮次 + 标题仅首次写入」三件事： 既减少高频路径上的加锁窗口，也让未登记过的历史会话被自动补齐， 而不是在列表里凭空消失。

调用时机（由应用层决定）

stream() 在进入图之前调用一次（turn_delta=1， 并带上用户输入作为标题），轮次结束时再调用一次（turn_delta=0，只刷新活动时间）。 这样即使首轮因模型初始化失败而早退，会话也已经存在；也因此 created_at 表示「首次发言时间」而不是「申请 ID 的时间」。 恢复执行同样只刷新时间——它是同一轮运行的延续，重复计数会让轮次失真。

12. 流程：HITL 中断与恢复

这是本工程最复杂的一条链路，涉及四个模块的协作。 触发条件是：execution_mode == "local" 且模型决定调用 execute。

中断阶段

1. HumanInTheLoopMiddleware 在 execute 执行前调用 interrupt()
2. LangGraph 产出 updates: {"__interrupt__": (Interrupt(value=HITLRequest, id=...),)}
3. translator._on_updates() 先识别 __interrupt__，交由 decode_interrupt 解析
4. 翻译器先 flush 未发送的工具调用，再产出 interrupt 事件
5. 事件经 SSE 到达前端 → renderApproval() 按 allowed_decisions 渲染按钮
   （CLI 侧：_run_turn 捕获 interrupt 载荷存进 pending_payload，跳出后调用 ask_human）

decode_interrupt()（application/interrupt_codec.py:58）兼容两种形态： 标准 HITL 的字典直接取 action_requests / review_configs； 非 HITL 的裸 interrupt() 会被包成统一形状（application/interrupt_codec.py:84-95）， 让前端只需处理一种结构。

恢复阶段

前端点击按钮 → 组装 decision → POST /resume
 └─ ResumeRequest 校验 type ∈ {approve,edit,reject,respond}
     └─ routes 转成 {"decisions": [...]}
         └─ build_resume_command() (:151)
             ├─ normalize_decisions() (:96) 逐条校验并补齐必需字段
             └─ Command(resume={"decisions": [...]})   # HITLResponse 的唯一合法形状

四种决策的语义差异

type必需字段行为
approve—按原参数执行
editedited_action.name（缺失即报错）用改写后的参数执行

链路一致性保证 CLI 的 _run_turn 在 while 循环中处理「一次运行多次中断」； Web 侧由前端在每次 interrupt 事件后重新发起 /resume。 两者最终都走同一个 build_resume_command，不存在两套格式。

操作路径关键实现

17. 关键设计决策汇总

为什么只保留一个 create_deep_agent 调用点？

参数组合会随 Backend、权限、技能、Profile 指数增长，散落调用必然导致护栏口径不一致， 也让安全审计失去锚点。所有装配变更都应集中在 agent/graph.py。

为什么模型用「懒加载 + 注册表」而不是启动时全部初始化？

模型初始化会读取密钥并可能触发鉴权探测。启动时一次性构造会让某个缺失 Key 的 provider 拖垮整个应用；懒加载 + 失败快照（在 SDK 调用前完成校验）让错误既早又准。

为什么 sandbox 档位不可用时抛异常而不是降级？

静默降级会让使用者误以为命令跑在隔离环境里，而实际作用在宿主机上—— 这是安全语义的欺骗，比启动失败严重得多。同理，auto 档位在候选 探测失败而回落到更弱档位时，会把跳过了哪些档位写进日志，而不是悄悄换一个。

为什么 disabled 档位不配审批？

disabled 下 execute 自身返回错误，再叠加审批只是让用户 反复确认一个注定失败的调用。local 与三个沙箱档位都默认 开启审批，文案按档位取值、写明该档的真实边界；sandbox 下只有显式设 SANDBOX_REQUIRE_APPROVAL=false 才会关闭，关闭时打告警。

为什么前端不用 EventSource？

它只支持 GET，而发起对话需要携带可能很长的 JSON 请求体。改用 fetch + ReadableStream 后，代价是需要手动处理分帧。

为什么服务层强制要求注入 checkpointer？

异步连接由上下文管理器托管，服务层自行创建就无从关闭；且没有 checkpointer 等于没有会话恢复与中断恢复能力，属于必须满足的前置条件——晚失败不如早失败。

为什么删除会话要绕过图的状态接口？

图的状态读取无法区分「空会话」与「不存在」，而 update_state 只追加写入， 删不掉历史记录。因此直接调用 checkpointer 的 adelete_thread。

18.2 已知限制

  • 模型供应商单一：注册表当前只注册 deepseek-flash，其余 provider 未接入。
  • 沙箱三档都不是安全边界：Tier 0（进程沙箱）/ Tier 1（WSL 发行版）/ Tier 2（容器）均已实现（2026-09-20 订正：此处原写「sandbox 档位未实现」，T24 落地后已不成立），它们解决的是「命令失控」而不是提权与逃逸—— Tier 1 经 /mnt 可读写宿主文件、且 WSL interop 允许反向启动 Windows 程序， Tier 2 共享宿主内核，三档都必须与人工审批配合。
  • 长期记忆无跨主体管理入口：记忆已持久化并按主体隔离，但 GET/DELETE /api/memories 只作用于调用者自己的那一份，管理员也无法 查看或清理他人记忆——跨主体读取需要独立的授权与审计设计，本期未做。
  • 会话搜索只覆盖标题：正文存在检查点的 msgpack BLOB 里，检索需要 逐条反序列化；要让正文可搜必须另建索引。（2026-09-20 补注：括号里原写 「会话导出 / 导入同样未做」，该半句已随 T19 交付而失效——导出 Markdown / JSON 与导入 均已实现。正文检索本身仍未做，此条继续有效；scripts/probe_fts5.py 留有当时的可行性验证。）
  • 归档与删除都不中断正在运行的任务：运行持有自己的图与检查点句柄， 删掉元数据后它仍会跑到结束并把事件推给发起方——需要「删除即停止」的场景得由 调用方先调 stop。
  • 检查点单机：SQLite 不适合多副本部署，横向扩展需替换为共享存储（如 PostgreSQL 检查点）。
  • 图缓存键不含 checkpointer：同一进程内切换 checkpointer 的场景需先改缓存键策略。
  • 无鉴权与会话隔离：Web 端点没有身份认证，任何能访问端口的人都能创建与 操作会话、读写工作区。代码里不存在认证子系统（2026-09-22 复核：此前这里记的 「disabled / apikey / oidc 三模式已交付」不成立—— 相关模块、认证端点与前端凭据文件均已不在仓库中）。缓解措施：默认 HOST=127.0.0.1、编排只绑回环；绑非回环地址会触发启动告警 （告警而非拒绝启动），那种组合必须自行提供网络边界。
  • tool/ 为空目录：早期文件工具原型已移除，功能由 deepagents 的内置工具承担。
  • 会话清单没有用户维度：list_threads 只按 limit / offset / 标题关键字 / 标签过滤，不与调用者身份绑定。 单主体形态下 thread_meta.owner_id 与运行登记表的 owner_id 恒为常量 local——它们是为多主体预留、当前不起隔离作用的字段， 而不是「跨用户读写返回 403」的凭据（2026-09-22 复核：代码里没有任何归属闸门）。 这与「无鉴权」是同一个问题的两面，服务端一旦多用户化必须同步补上。
  • 存量空会话需手工清理：新逻辑不再产生空会话，但升级前若已在旧版本下 打开或刷新过页面，库里会留下 title='' AND turn_count=0 的行，需一次性删除。
