## 二、三维度缺口分析

### 维度 1：用户需求视角（我想做的事做不了）

1. ✅ **能停了**：`stop` 端点 + 前端停止按钮 + 协作式取消；T7 补上取消后 2 秒内整棵进程树
   消失的进程层确认。
2. ✅ **能改能重来了**（T16）：消息可编辑、最后一轮可重新生成、可从历史某轮分叉；
   前端有分支栏，分叉后可切换。**仍缺**跨会话的分支对比视图（分支本身可切，但没有并排比较）。
3. ✅ **能看了**（T15）：工作区文件面板带目录树与内联预览（文本 / 图片 data URL），
   工具输出的「查看完整输出」按 `offset` 续取。产物可见性不再是空白。
4. ✅ **能传了**（T21）：图片附件上传、按 MIME 白名单与大小上限校验、按 `ModelSpec`
   的视觉能力判定——不支持的模型**显式报错**而不是静默丢图。
5. 🟡 **搜索仍只匹配标题**（T10）：侧栏有搜索框与「含已归档」开关；**仍缺**正文检索
   （正文在检查点 BLOB 里，需另建索引；`scripts/probe_fts5.py` 已做过技术验证但未落地）。
   会话**标签**的数据结构与端点已就位（`PATCH` 的 `tags` 分支、`tag` 过滤参数），
   **仍缺前端入口**——这是「差一步」的典型形态。
6. 🟡 **能带走了，但带不回来给别人**（T19）：会话可导出 Markdown / JSON、可导入；
   **仍缺**分享链接（导出需要对方也有这个系统的访问权）。
7. 🟡 **能换模型，仍不能换人格**：模型下拉已有多项可选（T5）；**temperature 等参数仍只藏在
   `.env`**，系统提示词仍硬编码于 `agent/profiles.py`，无自定义人格 / 角色模板（⑮）。

### 维度 2：业务流程视角（上线会断在哪一环）

1. ✅ **身份与归属已就位**：`thread_meta.owner_id` + 角色权限模型（viewer / member / admin）；
   跨用户读写会话会被 403 拦下，管理员是显式的运维兜底路径。
2. ✅ **审计已闭环**：审批决策、工具执行、会话增删改、记忆删除、越权拒绝全部落库，
   带请求来源（IP / UA）、`trace_id` 与归档保留策略。
3. 🟡 **计量仍缺成本侧**（T6）：每轮 token 用量可观测并可按用户 / 会话 / 时间窗聚合；
   **仍缺**费用估算与用量配额——成本控制目前只有 `MAX_MODEL_CALLS_PER_RUN=60`
   这一道粗粒度护栏。
4. ✅ **运维接口已闭环**（T4 + T18）：`/health`、`/ready`、`/metrics` 之外，`trace_id`
   已贯穿审计与用量落库并注入日志，日志支持结构化 JSON 输出。
   **仍缺** OpenTelemetry / `traceparent` 导出（接外部追踪系统），本期未做也未被列为目标。
5. 🟡 **中断兜底仍缺通知**：T7 补上中断 TTL（超期作废、拒绝过期审批）与运行超时强制取消；
   **仍缺**超期前的提醒与「谁该审批」的通知通道——有 TTL 但没有催办。
6. ✅ **运行治理已闭环**（T7 + T17）：运行超时强制取消、HITL 挂起 TTL、进程树回收之外，
   已有**全局并发上限**（`max_concurrent_runs`）与**按用户限流**（令牌桶，键为 `owner_id`），
   以及 per-thread 互斥（`ThreadBusyError`）。**仍缺**优先级队列（所有运行目前平等排队）。
7. 🟡 **数据生命周期仍缺两件**：审计归档与保留策略、会话删除时的检查点清理、会话归档
   （软删除回收站）已落地；**仍缺**①**通用迁移版本管理**——现状是知识库有
   `_SCHEMA_VERSION` 校验、会话表有顺序执行的 `_MIGRATIONS` 列表（靠吞异常跳过已存在列）、
   三个 store 各自手写 `ALTER TABLE ADD COLUMN ... try/except`，没有 `PRAGMA user_version`
   也没有统一的迁移表；②**孤儿检查点定期清理**（检查点只在会话删除时同步清理，
   审计有定期任务而检查点没有）。

## 五、结论

**内核与安全设计是超额完成的**（分层、护栏、沙箱、HITL、权限裁剪都做到了生产级思考）。
经过 T1 → T25，原先「几乎为零」的那一侧不但补上，而且补得比计划更宽：
**身份、控制、可见性、可运维、可计量、可追溯** 全部就位，
信息获取（⑤）、产物可见性（⑬）、交互闭环（⑨）、多模态（⑯）、知识库（⑲）、
技能体系（⑳）、容器隔离（㉒）、交付流水线（㉔）逐项落地。

当前的短板与上一轮的判断已经不同：

1. **不再有「能力空白」**。剩余 4 项未完成全部是 P2/P3——它们影响「这个助手有多顺手」，
   不影响「这个助手能不能用」。这是一个阶段性的变化：从「补缺失」转成「补余量」。
2. **最大的实际风险是验证而非实现**。⑤ 的真机端到端验收、T24 的 Docker Hub 依赖、
   首次索引的模型下载，都是「代码已就绪、环境未闭环」——这类问题的代价会随部署环境
   数量放大，值得单独安排一轮真机验收，而不是继续堆功能。
3. **生产化收尾仍是团体的门槛**：费用配额、故障转移、迁移版本管理、CI 静态检查
   ——没有它们，系统能自用、能小范围交付，但不好交给一个团队长期运维。

建议的下一步：**先做一轮「真机验收巡检」**（把 ④ 里那些「代码就绪、环境未闭环」的项
逐条在有出网条件的环境补验），再进入费用与配额。理由与上一轮同源：一项能力值不值得
继续投入，取决于它是否真的按预期工作，而不取决于它有没有被写出来。
