# 认证与鉴权库评估（FastAPI 生态）

> **结论先行：不引入认证框架库。** 现有 API Key 实现（`interfaces/web/auth/` +
> `application/principal.py`）与真实需求匹配，替换成任何用户管理框架都会引入我们
> 不需要的一整套概念（注册、密码、找回、会话），而收益是零。
>
> 本文同时给出**什么时候应该重新评估**，以及届时该选哪一个。

评估日期：2026-09-19。背景：本项目刚移除了自建的 OIDC 对接（见提交记录），
认证模式收敛为 `disabled` 与 `apikey` 两种。

## 一、先把需求说清楚（这是我们评判的唯一尺子）

从代码事实出发，而不是从「一般 Web 应用需要什么」出发：

| 事实 | 出处 |
| --- | --- |
| 调用方是**持有密钥的机器**：CLI、脚本、集成方 | `interfaces/cli.py` 读 `HARNESS_API_KEY`；前端无登录入口 |
| 凭据由**运维下发**（`/auth/api-keys` 创建、可吊销、可设过期） | `interfaces/web/auth/apikey.py`、`runtime/api_key_store.py` |
| 权限模型是「角色 → 固定权限集合」 | `application/principal.py` 的 `ROLE_PERMISSIONS` + `require_permission` |
| 每个请求都要有主体，且主体只有一处定义 | `interfaces/web/auth/deps.py` 的 `get_principal` |
| 需要审计、限流、开发用单 key 快速入口 | `log_auth_event`、`RateLimiter`、`auth_api_key_dev` |

**明确不需要的**：用户自助注册、密码存储与找回、邮箱验证、多租户组织、社交登录、
浏览器会话与「记住我」。这正好是用户管理框架的主战场——也是它们与本案的错配点。

## 二、候选与判定

维护状态为 **2026-09-19 经 GitHub API 实测**（`stars` 与 `last_push` 是粗信号：
最后一次提交也可能只是 CI 或文档，不能当作「有人在维护 API」的证据）。

| 候选 | 它解决的问题 | 与本案匹配度 | 实测状态 |
| --- | --- | --- | --- |
| `fastapi-users` | 完整用户生命周期：注册/登录/JWT/密码重置/邮件 | **错配**：我们没有用户可管 | 6,241 stars；未归档；最后提交 2026-08-17；官方声明**只做安全与依赖维护，不再加新功能** |
| `AuthX` | 令牌与会话管理、OAuth2 客户端 | **暂不需要**：它围绕「会话」设计，而我们没有会话 | 1,196 stars；最后提交 2026-09-18（活跃） |
| `authlib` | OAuth2 / OIDC **协议**实现（客户端与提供方） | **将来重接 IdP 时的正确选择** ✗ 当前无 IdP | 5,424 stars；最后提交 2026-08-31（活跃） |
| `PyJWT` / `itsdangerous` | 签发与校验令牌的原子能力 | 只有在需要「签发令牌」时才有意义 | 已随 OIDC 一起移除 |
| `pycasbin` | 模型化鉴权（RBAC / ABAC，策略文件驱动） | **规则规模不够**：我们是一条角色映射表 | 1,767 stars；最后提交 2026-08-13（活跃） |
| 托管服务（Auth0 / Clerk / Supabase / WorkOS 等） | 外包整个认证与用户体系 | **与「本地优先、无外部依赖」冲突** | 不适用 |

## 三、为什么「不引库」在这里是结论，而不是偷懒

1. **库解决的是「用户生命周期」，我们没有生命周期可管。** 凭据由运维下发、可吊销，
   没有注册、没有密码、没有找回——把这类框架引进来，会新增比它替换掉的代码更多的
   配置与概念。
2. **主体的构造权现在收在一处。** `Principal` 在 `application/principal.py` 定义，
   全仓的权限判断都挂在它上面；引库意味着把这个构造过程交给框架，而它带来的
   `user` 模型与我们的 `Principal` 必然要写一层映射——那层映射就是新的出错面。
3. **每多一个依赖，就多一条供应链与升级路径。** 这条路径上的收益是零（见第 1 点），
   成本却要在每次安全更新与版本升级时支付。
4. **当前实现的安全要点是有意为之的**：密钥比较用 `secrets.compare_digest`（防时序侧信道）、
   失败与成功都落审计、认证端点按 IP 限流。这些不依赖任何框架。

## 四、什么时候应该重新评估（触发条件）

出现下列任一情况时，本结论失效，按对应一列选型：

| 触发条件 | 选择 | 理由 |
| --- | --- | --- |
| 需要**浏览器登录与会话**（人用界面，而非机器调用） | `AuthX`（活跃） | 会话/令牌是它的核心能力；不必自己写 Cookie 与刷新逻辑 |
| 需要**重新对接外部 IdP**（OIDC/LDAP） | `authlib` | 用协议实现库，**不要**再自写 discovery / JWKS / ID Token 验签——上一轮踩的坑（issuer 两侧可达性、grant_types、PKCE）几乎都在这些细节里 |
| 需要**多用户自助注册 / 找回密码** | `fastapi-users` 或 `AuthX` | 此时才真正需要用户表与用户生命周期；注意 `fastapi-users` 已进入维护模式，新项目应优先看 `AuthX` |
| **权限规则复杂到需要策略文件**（按资源、按属性、按条件） | `pycasbin` | 一条角色映射表够用时不要引它；规则开始需要组合与继承时才划算 |
| 需要**对外开放接口并给第三方发凭据** | 仍是自建（现有 `/auth/api-keys` + scopes） | 这就是当前形态的放大版，没有新概念要引入 |

## 五、评估口径与局限

- 数据来源：`api.github.com` 实测（stars / archived / pushed_at）+ 本仓库代码事实。
- **局限一**：`last_push` 不能证明 API 有人在维护，只能排除「彻底停更」。
- **局限二**：本评估不含对上述库的**实测**（未安装、未跑通任何一条链路）。
  结论建立在本项目**不需要**它们提供的能力之上；一旦第 4 节的触发条件成立，
  应改为「先跑通最小链路再选型」，而不是照本表直接采用。
