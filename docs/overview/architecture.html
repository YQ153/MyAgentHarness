1. 项目定位与技术栈

MyAgentHarness 是一个通用任务 Agent 的骨架工程。它不是某个垂直业务机器人， 而是一套「把大模型变成能干活的助手」所需的完整基础设施：受限于工作区的文件读写、 任务规划与待办、子任务委派、高危操作的人工审批、会话持久化与长期记忆。

工程的核心特征是 双形态同内核：命令行（CLI）与 Web 服务共享同一套 应用服务与 Agent 内核，两者的差异被严格压缩在「事件怎么渲染」和「人工决策从哪来」 两个适配点上。

4. 核心组件：配置中心

config.py 是全应用唯一的环境变量解析点，读取优先级为 环境变量 > .env 文件 > 字段默认值（config.py:313-318）。 选用 pydantic-settings 而非裸 os.getenv，是为了让类型转换、 缺省值与非法值拦截由框架统一处理。

三类字段

  • 模型与 LLM 参数：deepseek_*、llm_temperature（限 0–2）、llm_timeout（>0）、llm_max_retries（>=0）。
  • 运行时路径：workspace、memory_file、db_path、skill_dirs。
  • 安全与护栏：execution_mode、shell_timeout、shell_max_output_bytes、max_model_calls_per_run、recursion_limit。

路径处理的两个关键约定

1. 路径统一展开为绝对路径 _expand_path（config.py:912）对 workspace / memory_file / db_path 执行 expanduser().resolve()。 WHY：Backend 的 root_dir 若为相对路径，进程工作目录一旦变化就会指向不同物理目录。
2. 传给 deepagents 的路径必须是「相对工作区的 POSIX 路径」 skill_source_paths()（config.py:1180）与 memory_paths （config.py:1204）都做了 relative_to(workspace) 再前置 /。 WHY：虚拟文件系统内部以 / 为根分隔符，且 Backend 的根就是 workspace； 传宿主机绝对路径（Windows 下还带盘符与反斜杠）永远命中不了。位于工作区之外的目录无法映射，只能跳过并告警。

existing_skill_dirs()（config.py:1156）在技能目录缺失时只记录告警 而不报错——技能库属于可选能力，缺失应当降级而非让应用无法启动。

8.2 runtime/store.py：长期记忆

open_store() 以异步上下文的方式提供 langgraph.store.sqlite.aio.AsyncSqliteStore，与检查点共用 DB_PATH 指向的同一个 SQLite 文件。WHY 用 SQLite 实现而不是 InMemoryStore：后者的生命周期与进程一致，重启即失，而文档与 /memories/ 路由承诺的是「跨会话记忆」；而 SQLite 版 Store 由 langgraph-checkpoint-sqlite 附带，本项目已依赖该包，因此是零新增依赖的替换。

两个必须显式设置的 PRAGMA：journal_mode=WAL（库级持久属性，但本模块 不应假设初始化顺序）与 busy_timeout=5000（连接级属性， 缺了它会在与审计 / 用量表并发写入时立刻抛 database is locked，而 Agent 写记忆恰好发生在运行中途）。必须用 AsyncSqliteStore 而非同步版： 图内的文件工具走异步 backend，而该实现的同步接口在事件循环里会直接抛 InvalidStateError。

管理口径 管理接口（application/memory_service.py + GET/DELETE /api/memories） 直接读写同一个 store 实例，命名空间同样按主体收敛，因此面板与 Agent 看到的是同一份数据。 存储层的键是去掉 /memories 挂载点的相对路径 （/notes.md），对外统一还原成 /memories/notes.md。

8.3 runtime/thread_store.py：会话元数据表

检查点表只保存图状态，其 metadata 是 LangGraph 自用字段 （source / step / writes），既没有标题也没有时间戳， 而会话列表恰恰需要这两项。靠反序列化 BLOB 凑列表成本极高（每条会话都要解包 msgpack）， 因此另建一张窄表 thread_meta，与检查点共用同一个 SQLite 文件—— 两者描述的是同一批会话，分库会带来「删了会话却删不掉元数据」的跨库不一致。

记录一轮对话：单条 UPSERT（runtime/thread_store.py:463）

INSERT INTO thread_meta (thread_id, title, created_at, updated_at, turn_count)
VALUES (?, ?, ?, ?, ?)
ON CONFLICT(thread_id) DO UPDATE SET
    updated_at = excluded.updated_at,
    turn_count = thread_meta.turn_count + ?,

一次往返同时完成「刷新活动时间 + 累加轮次 + 标题仅首次写入」三件事： 既减少高频路径上的加锁窗口，也让未登记过的历史会话被自动补齐， 而不是在列表里凭空消失。

调用时机（由应用层决定）

stream() 在进入图之前调用一次（turn_delta=1， 并带上用户输入作为标题），轮次结束时再调用一次（turn_delta=0，只刷新活动时间）。 这样即使首轮因模型初始化失败而早退，会话也已经存在；也因此 created_at 表示「首次发言时间」而不是「申请 ID 的时间」。 恢复执行同样只刷新时间——它是同一轮运行的延续，重复计数会让轮次失真。

会话真正诞生 POST /api/threads/{id}/runs 在进入图之前由 _record_turn() 以 UPSERT 登记， 标题取自本次输入；created_at 因此等于「首次发言时间」而非「申请 ID 的时间」
列出会话 GET /api/threads?query=&include_archived= 只读元数据表，按 updated_at 倒序分页返回，不触碰任何图状态； query 只匹配标题——正文存在检查点的 msgpack BLOB 里， 逐条反序列化检索是另一个量级的成本，这条边界写在接口与文档上，比让它表现成 「搜索偶尔很慢」更诚实
重命名 / 归档 PATCH /api/threads/{id} 局部更新：title 与 archived 至少给一项，空请求体直接 400 （避免产出「返回成功但什么都没改」这种无法归因的结果）。权限走 thread:update——归档可逆、改名无破坏性，与「把数据删掉」不是同一风险量级。 两项同时给时在同一次请求内顺序执行，省掉「改成功了但归档失败了」的中间态
读取历史 GET /api/threads/{id} graph.aget_state(cfg) → values["messages"] → ThreadService._message_to_dto 统一成 HistoryMessage； 会话不存在返回空列表，查询失败则抛错（不再把故障伪装成空列表）
删除会话 DELETE /api/threads/{id} 先删 thread_meta 再删检查点；返回的 deleted 以元数据为准——adelete_thread 对不存在的会话是静默成功的 no-op，若用它判断，删除一个从未发言过的 ID 也会报成「已删除」。 WHY 不通过图的状态接口：读状态无法区分「空会话」与「不存在」， 而 update_state 只会追加写入，删不掉历史

前端的接入情况：init() 只拉取模型与清单，随后按 URL 决定进入草稿态还是恢复历史； 点击侧栏条目切换会话，发出首条消息时才申请 ID 并写入地址栏。 删除接口目前只在 REST 层提供，界面尚未暴露按钮。

14.1 统一事件模型（application/events.py）

CLI 与 Web 消费同一套事件定义，避免同一件事实在两处各写一遍渲染逻辑。 AgentEvent 是冻结数据类——事件一旦生成就不应被下游修改。 WHY 不以 SSE 命名：它描述的是「运行过程中发生了什么」，与传输方式无关； CLI 直接渲染到终端，只有 Web 才经 encode_sse() 序列化成文本帧。

17. 关键设计决策汇总

为什么只保留一个 create_deep_agent 调用点？

参数组合会随 Backend、权限、技能、Profile 指数增长，散落调用必然导致护栏口径不一致， 也让安全审计失去锚点。所有装配变更都应集中在 agent/graph.py。

为什么模型用「懒加载 + 注册表」而不是启动时全部初始化？

模型初始化会读取密钥并可能触发鉴权探测。启动时一次性构造会让某个缺失 Key 的 provider 拖垮整个应用；懒加载 + 失败快照（在 SDK 调用前完成校验）让错误既早又准。

为什么 sandbox 档位抛异常而不是降级？

静默降级会让使用者误以为命令跑在容器里，而实际作用在宿主机上—— 这是安全语义的欺骗，比启动失败严重得多。

为什么 HITL 只在 local 档位开启？

disabled 下 execute 自身返回错误，再叠加审批只是让用户 反复确认一个注定失败的调用；sandbox 由沙箱本身提供隔离保证。

为什么前端不用 EventSource？

它只支持 GET，而发起对话需要携带可能很长的 JSON 请求体。改用 fetch + ReadableStream 后，代价是需要手动处理分帧。

为什么服务层强制要求注入 checkpointer？

异步连接由上下文管理器托管，服务层自行创建就无从关闭；且没有 checkpointer 等于没有会话恢复与中断恢复能力，属于必须满足的前置条件——晚失败不如早失败。

为什么删除会话要绕过图的状态接口？

图的状态读取无法区分「空会话」与「不存在」，而 update_state 只追加写入， 删不掉历史记录。因此直接调用 checkpointer 的 adelete_thread。

18.2 已知限制

  • 模型供应商单一：注册表当前只注册 deepseek-flash，其余 provider 未接入。
  • sandbox 档位未实现：需接入外部沙盒实现后才能启用。
  • 长期记忆无跨主体管理入口：记忆已持久化并按主体隔离，但 GET/DELETE /api/memories 只作用于调用者自己的那一份，管理员也无法 查看或清理他人记忆——跨主体读取需要独立的授权与审计设计，本期未做。
  • 会话搜索只覆盖标题：正文存在检查点的 msgpack BLOB 里，检索需要 逐条反序列化；要让正文可搜必须另建索引。（2026-09-20 补注：括号里原写 「会话导出 / 导入同样未做」，该半句已随 T19 交付而失效——导出 Markdown / JSON 与导入 均已实现。正文检索本身仍未做，此条继续有效；scripts/probe_fts5.py 留有当时的可行性验证。）
  • 归档与删除都不中断正在运行的任务：运行持有自己的图与检查点句柄， 删掉元数据后它仍会跑到结束并把事件推给发起方——需要「删除即停止」的场景得由 调用方先调 stop。
  • 检查点单机：SQLite 不适合多副本部署，横向扩展需替换为共享存储（如 PostgreSQL 检查点）。
  • 图缓存键不含 checkpointer：同一进程内切换 checkpointer 的场景需先改缓存键策略。
  • 无鉴权与会话隔离：Web 端点没有身份认证，任何能访问端口的人都能创建与操作会话。 已完成（T1，2026-09-20 补注）：现有 disabled / apikey / oidc 三种模式，认证端点另有 IP 级限流。仍然要注意： AUTH_MODE=disabled 时服务没有任何身份，此时把 HOST 改绑非回环地址 会触发启动告警（告警而非拒绝启动），那种组合依然只适合本机。
  • tool/ 为空目录：早期文件工具原型已移除，功能由 deepagents 的内置工具承担。
  • 会话清单没有用户维度：接口返回库中的全部会话，不与调用者身份绑定。 这与「无鉴权」是同一个问题的两面，服务端一旦多用户化必须同步处理。 已完成（T1）：清单按 thread_meta.owner_id 收敛，跨用户读写返回 403； 管理员是显式的运维兜底路径（不是绕过归属的隐式后门）。
  • 存量空会话需手工清理：新逻辑不再产生空会话，但升级前若已在旧版本下 打开或刷新过页面，库里会留下 title='' AND turn_count=0 的行，需一次性删除。
