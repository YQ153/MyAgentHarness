## 第一部分 基础概念

### 1.1 一句话区分

| | 英文 | 回答的问题 | 本质 |
| --- | --- | --- | --- |
| **认证** | Authentication（AuthN） | **你是谁？** | 身份校验，证明主体确实是其声称的身份 |
| **鉴权** | Authorization（AuthZ） | **你能做什么？** | 权限校验，判定已认证的主体是否有权执行某操作 |

> 记忆口诀：**AuthN = Name**（身份），**AuthZ = Zone**（活动范围）。

### 1.2 经典类比：机场登机

```
出示护照 + 人脸识别   →  认证（AuthN）：确认你是张三本人
     ↓
打印登机牌（舱位 C / 座位 32A / 可进贵宾厅？）
     ↓
登机口核验登机牌权限  →  鉴权（AuthZ）：确认你有权上这架飞机、坐这个舱位
     ↓
全程监控录像留痕      →  审计（Accounting/Audit）：事后可追溯
```

**关键观察**：登机牌不会重新证明你是谁（认证已完成），它只携带凭证；而贵宾厅、廊桥、驾驶舱是三道不同的鉴权关卡。这种「凭证 + 关卡」的分离，是所有现代鉴权架构的基础。

### 1.3 顺序不可颠倒

认证**必须先于**鉴权发生——不知道主体是谁，就无法判定它该有什么权限。

```
请求
 │
 ├─(1) 提取凭证 ────────────── 无凭证 ──→ 401 Unauthorized（未认证）
 │
 ├─(2) 验证凭证真伪 ────────── 凭证无效/过期 ──→ 401
 │
 ├─(3) 得到身份 Principal ──── 认证完成（AuthN ✓）
 │
 ├─(4) 查策略，判定权限 ────── 权限不足 ──→ 403 Forbidden（已认证但无授权）
 │
 ├─(5) 放行执行 ────────────── 鉴权完成（AuthZ ✓）
 │
 └─(6) 记录审计日志 ────────── Accounting ✓
```

> **HTTP 状态码的常见误解**：`401 Unauthorized` 字面像是「未授权」，实际语义是「未认证」（RFC 7235 原文用词如此，响应头是 `WWW-Authenticate`）。真正表示「认证通过但权限不足」的是 `403 Forbidden`。

### 1.4 AAA 模型与周边概念

现代身份体系通常归入 **AAA** 框架：

| 环节 | 全称 | 职责 | 典型产物 |
| --- | --- | --- | --- |
| **认证** | Authentication | 确认身份 | Session、JWT、id_token |
| **鉴权** | Authorization | 授予 / 判定权限 | ACL、Role、Policy、Scope |
| **审计** | Accounting / Audit | 记录与追溯行为 | 审计日志、SIEM 事件 |

其他高频术语：

| 术语 | 含义 |
| --- | --- |
| **Identification（标识）** | 声称身份（如填用户名）。认证 = 标识 + 证明 |
| **Principal（主体）** | 认证通过后系统内部使用的身份对象（用户 / 服务 / 设备） |
| **IAM** | Identity and Access Management，身份与访问管理的总称 |
| **SSO** | 单点登录，一处登录多处通行 |
| **IdP** | Identity Provider，身份提供者（签发身份断言的一方） |
| **SP / RP** | Service Provider / Relying Party，依赖 IdP 的应用方 |
| **Federation（联邦）** | 多组织间互信，A 组织的身份可在 B 组织的系统中使用 |
| **Session（会话）** | 认证状态的服务端表现形式 |
| **Claim（声明）** | 关于主体的断言，如 `email=...`、`role=admin` |

## 第二部分 认证因子：一切方案的底层分类

所有认证方案本质上都是对以下四类因子的不同组合：

| 因子类别 | 英文 | 举例 | 被盗难度 | 用户体验 |
| --- | --- | --- | --- | --- |
| **知识因子** | something you know | 密码、PIN、安全问题、助记词 | 低（可钓鱼、可撞库、可肩窥） | 好 |
| **持有因子** | something you have | 手机（OTP / 推送）、硬件 Key、智能卡、证书私钥 | 中高（需物理接触） | 中 |
| **固有因子** | something you are | 指纹、人脸、声纹、虹膜 | 高（难复制） | 好 |
| **位置 / 行为因子** | somewhere you are / something you do | 可信网络、地理围栏、击键动力学、异常登录检测 | 中 | 无感 |

由此衍生：

- **单因素认证（SFA / 1FA）**：只用一类因子，典型如「仅密码」。安全性最低，正被行业逐步淘汰。
- **多因素认证（MFA / 2FA）**：组合**不同类别**的因子。注意——「密码 + 短信验证码」是 2FA，但「密码 + 另一个密码」不是。
- **无密码认证（Passwordless）**：摒弃知识因子，改用持有 + 固有因子（如 Passkey）。同时提升安全性与体验，是当前主流演进方向。

> NIST SP 800-63B 定义了三档认证保证等级：**AAL1**（单因素）、**AAL2**（多因素）、**AAL3**（多因素 + 硬件加密认证器）。金融、医疗等场景通常要求 AAL2 以上。

### 3.1 基于会话的认证（Session-Cookie）

**流程：**

```
① POST /login {username, password}
② 服务端校验凭据（比对密码哈希）
③ 生成随机 session_id（128bit+ CSPRNG），写入服务端存储（Redis / DB）
   store[session_id] = {user_id, roles, expires_at, ip, ua}
④ Set-Cookie: session_id=xxx; HttpOnly; Secure; SameSite=Lax; Path=/
⑤ 后续请求浏览器自动携带 Cookie
⑥ 服务端每个请求查一次存储 → 取出 Principal → 进入鉴权
```

**优点：**

- **可即时吊销**：删除服务端记录即刻失效，这是无状态令牌难以做到的核心优势
- **服务端完全可控**：可强制下线、可查看在线会话列表、可限制并发登录数
- Cookie 由浏览器自动管理，`HttpOnly` 下前端 JS 无法读取，**天然免疫 XSS 窃取**
- 实现简单，无需理解签名算法与密钥管理

**缺点：**

- **服务端存状态**：分布式下需要共享存储（Redis）或会话粘性，扩容与跨区部署成本高
- 每个请求都要查存储，**有额外 I/O 往返**（可用本地缓存缓解）
- **CSRF 风险**：浏览器自动携带 Cookie 是双刃剑，需要 `SameSite` + CSRF Token 双重防护
- 跨域场景（多域名、前后端分离部署在不同域）下 Cookie 传递受限
- 天然不适合原生 App 与非浏览器客户端

**适用场景：** 传统服务端渲染 Web 应用、企业内部后台、对「即时踢下线」有强需求的场景。

**安全要点：**

- Cookie 必须 `HttpOnly`（防 XSS 读取）+ `Secure`（仅 HTTPS）+ `SameSite=Lax|Strict`（防 CSRF）；高敏感场景加 `__Host-` 前缀，锁定域名与路径
- **防范会话固定（Session Fixation）**：登录成功后**必须**重新生成 session_id，不能沿用登录前的值
- 登出必须同时清除服务端记录，仅删客户端 Cookie 等于「换了个门牌号的同一把钥匙」
- 设置绝对超时 + 空闲超时双策略
- 记录 IP / UA 并在变更时要求重新认证

### 3.2 基于令牌的认证（Token-Based）

#### 3.2.1 两类令牌的根本差异

| | **不透明令牌（Opaque Token）** | **自包含令牌（JWT / JWS）** |
| --- | --- | --- |
| 形态 | 无意义随机串（如 `at_9f8e7d...`） | `Header.Payload.Signature` 三段 Base64URL |
| 校验方式 | 必须回源查询 / introspection（RFC 7662） | 本地验签即可，**无需回源** |
| 状态 | 有状态 | 无状态（服务端不存） |
| 即时吊销 | **可以**（删除服务端记录） | **不可**（已签发无法收回） |
| 每次校验开销 | 一次网络 / DB 往返 | 一次 CPU 验签（更快） |
| 适用场景 | 需要强管控的内部令牌 | 跨服务传递、高并发 API |

**取舍本质**：要不要用「即时吊销能力」换取「无状态横向扩展性」。

#### 3.2.2 JWT 结构详解

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9  .  eyJzdWIiOiIxMjM0NS...  .  TUtLaWQ...
└─────────── Header ───────────────┘    └──── Payload ────┘    └─ Signature ─┘
   {"alg":"RS256","typ":"JWT",             Claims:               签名
    "kid":"2026-09-key"}                   sub / iss / aud
                                           exp / iat / nbf
                                           jti / scope / custom
```

**标准 Claim（Registered Claims）：**

| Claim | 含义 | 作用 |
| --- | --- | --- |
| `iss` | Issuer，签发者 | 防止跨签发方混淆 |
| `sub` | Subject，主体标识 | 「这是谁」 |
| `aud` | Audience，受众 / 目标服务 | 防止令牌被投到别的 API 使用 |
| `exp` | Expiration Time，过期时间 | 有效期边界 |
| `nbf` | Not Before，生效时间 | 提前签发 / 密钥轮换过渡 |
| `iat` | Issued At，签发时间 | 判断令牌「年龄」 |
| `jti` | JWT ID，唯一标识 | 去重 / 重放检测 / 黑名单 key |

> **Payload 只做 Base64URL 编码，不是加密！** 任何人都可解码读取。**绝不能放密码、身份证、密钥等敏感数据**。需要机密性时应使用 **JWE**（加密型 JWT，RFC 7516）。

**签名算法选择：**

| 算法 | 类型 | 密钥 | 适用 |
| --- | --- | --- | --- |
| `HS256` | 对称 | 共享密钥 | 单一可信域内，签发方与校验方为同一实体 |
| `RS256` / `PS256` | 非对称 RSA | 私钥签 / 公钥验 | **多方场景推荐**：资源方只需公钥，无法伪造签发 |
| `ES256` | 非对称 ECDSA | 私钥签 / 公钥验 | 签名更短更快，新一代首选 |

> 应以非对称为主：**JWT 的信任边界很微妙**——凡能验签的服务如果同时持有对称密钥，也就获得了伪造令牌的能力。

#### 3.2.3 JWT 的经典痛点与解法

| 痛点 | 说明 | 解法 |
| --- | --- | --- |
| **无法即时吊销** | 签发后在 `exp` 前始终有效 | ① 短 TTL（5~15min）+ Refresh Token ② 维护 `jti` 黑名单（仅用于踢下线，仍需短 TTL 兜底） ③ 密钥版本化 / `kid` 轮换使全量失效 ④ 关键操作前回源查用户状态 |
| **令牌体积大** | 每个请求都带上 | 只放必要 claim；或改用 reference token（令牌即句柄，回源换详情） |
| **令牌泄漏即完全失守** | 持有者即被信任 | 绑定上下文（IP / UA / 设备指纹）；**DPoP**（RFC 9449）或 **mTLS 证书绑定**（RFC 8705）实现 sender-constrained token |
| **过期策略粗糙** | 难以兼顾「续期」与「安全」 | Access Token 短 + Refresh Token 长，**Refresh Token 轮换**并检测重放（检测到复用即吊销全族） |
| **时钟偏移** | 分布式部署时钟不一致 | 允许 30~60s leeway，同时全链路 NTP 同步 |

#### 3.2.4 令牌该存在哪儿

| 存储位置 | XSS 风险 | CSRF 风险 | 适用 |
| --- | --- | --- | --- |
| `localStorage` / `sessionStorage` | **高**（JS 可读，XSS 直接窃取） | 低（不自动发送） | 纯 API 调用、跨域场景、能严格管控第三方脚本 |
| `HttpOnly` Cookie | 低（JS 不可读） | **高**（自动携带） | Web 应用主流选择，需配 SameSite + CSRF Token |
| 内存（闭包 / state 变量） | 中（页面刷新即失） | 低 | SPA 配合 refresh 换取，权衡后的折中方案 |

> 没有完美答案。**通用建议**：能用 `HttpOnly + Secure + SameSite` Cookie 就用；SPA 若用内存存储，则必须有可靠的 refresh 机制，并接受「刷新页面需重新换取」。

#### 3.2.5 适用场景

SPA + 移动端 + 第三方 API 调用；微服务间身份传递。

### 3.3 OAuth 2.0 — 授权框架（不是认证协议！）

> **最常见的认知错误**：OAuth 2.0 解决的是「**我要不要把我的权限交给第三方**」，它不告诉你用户是谁。**用 OAuth 2.0 做登录等于把授权当认证用**，会造成「任何人拿到任意 access_token 都能冒充登录」的漏洞。要做登录必须用其上的 OIDC（见 3.4）。

**四种角色：**

```
┌──────────────┐         ┌──────────────────┐         ┌──────────────┐
│  Resource    │         │      Client      │         │ Authorization│
│    Owner     │         │   （第三方应用）  │         │    Server    │
│   （用户）    │         │                  │         │              │
└──────┬───────┘         └────────┬─────────┘         └──────┬───────┘
       │  授予 / 拒绝              │                          │
       └──────────────────────────▶│  ① 请求授权               │
                                   │─────────────────────────▶│
                                   │  ② 返回授权码 code        │
                                   │◀─────────────────────────│
                                   │  ③ code + secret 换 token │
                                   │─────────────────────────▶│
                                   │  ④ 返回 access_token      │
                                   │◀─────────────────────────│
                                   │  ⑤ 携带 token 访问资源     │
                                   │─────────────────────────▶ Resource Server
```

**授权模式（Grant Types）演进：**

| 模式 | 状态 | 说明 |
| --- | --- | --- |
| **Authorization Code + PKCE** | ✅ **当前唯一推荐的公共客户端模式** | 授权码经浏览器重定向传递，令牌经后端直连换取；PKCE（RFC 7636）用一次性 `code_verifier` 防止授权码截获攻击 |
| Client Credentials | ✅ 推荐（机器对机器） | 无用户参与，用 client_id + secret / 私钥换取服务自身令牌 |
| Device Authorization（RFC 8628） | ✅ 推荐（输入受限设备） | 电视 / CLI 工具：设备显示码，用户在手机上确认 |
| Refresh Token | ✅ 配套机制 | 换取新 access_token；**公共客户端必须轮换并检测重放** |
| Implicit（隐式） | ❌ **已废弃** | 令牌直接从 URL fragment 返回，易泄漏于浏览器历史与 Referer |
| Resource Owner Password Credentials | ❌ **已废弃** | 应用直接代持用户密码，违背 OAuth 的全部设计初衷 |

**核心概念：**

- **Scope**：权限范围声明（如 `read:threads write:files`），是 OAuth 世界里的粗粒度鉴权
- **Access Token**：访问资源的凭证，对客户端**不透明**，格式由 AS 决定（JWT 或不透明串皆可）
- **Consent 页面**：用户显式知情同意的环节，是 OAuth 合法性的基础，**不可省略**
- **DPoP / mTLS 绑定**（RFC 9449 / 8705）：让令牌与持有者密钥绑定，失窃后无法冒用

**OAuth 2.1** 整合了近年最佳实践：**强制 PKCE**、移除隐式与密码模式、`redirect_uri` 要求精确匹配、Refresh Token 要求轮换或 sender-constrained。

**适用场景：** 第三方授权接入、开放平台、微服务间委派、「使用 X 登录」的底层（配合 OIDC）。

### 3.4 OpenID Connect（OIDC）— OAuth 2.0 之上的身份层

**解决的问题**：OAuth 2.0 缺「这是谁」的标准答案，各家自定义 `/me` 字段混乱；OIDC 把它标准化。

**在 OAuth 2.0 基础上增加了：**

| 新增物 | 说明 |
| --- | --- |
| `scope=openid` | 显式声明「我要做登录」 |
| **`id_token`** | **JWT 格式**的身份令牌，含 `sub`（用户唯一标识）、`iss`、`aud`、`exp`、`nonce`，可选 `email` / `name` / `picture` |
| **UserInfo Endpoint** | 标准用户信息接口，用 access_token 换取更多 claim |
| **Discovery**（`/.well-known/openid-configuration`） | 自动发现签发者、端点地址、支持的算法与 JWKS 地址 |
| **标准 Claims** | 跨 IdP 统一的字段名，无需为每个 IdP 写适配 |

**典型流程（Authorization Code + PKCE）：**

```
① 重定向到 IdP：?response_type=code&scope=openid profile email
                 &nonce=NONCE&code_challenge=...&code_challenge_method=S256
② 用户在 IdP 登录并同意
③ 回调携带 code
④ 后端用 code + PKCE verifier 换 id_token + access_token
⑤ 校验 id_token：签名 / iss / aud / exp / nonce（防重放）
⑥ 从 sub 得到稳定用户标识 → 建立本地会话
```

**OIDC 的三种响应类型：**

| Flow | response_type | 特点 |
| --- | --- | --- |
| Authorization Code | `code` | **最安全**，令牌不经浏览器 URL，推荐 |
| Implicit | `id_token token` | 已不推荐（令牌暴露于 URL） |
| Hybrid | `code id_token` | 兼顾首屏与后端校验，仍有 URL 暴露，慎用 |

> **注意事项**：`id_token` 只用于「向客户端证明用户身份」，**不要拿 id_token 当 API 的 Bearer Token 用**——API 应使用 access_token。两者的 `aud` 不同：id_token 的 `aud` 是 client_id，access_token 的 `aud` 是资源服务器。

**适用场景：** 现代 SSO、「使用 Google / 企业微信登录」、需要跨应用统一身份的 SaaS。

---

### 3.5 SAML 2.0 — 企业级联邦的既成事实标准

**形态**：基于 XML 的断言（Assertion）协议，2005 年定稿，历史包袱重但企业渗透率极高。

**核心流程：**

```
User → SP（Salesforce / Jira / 内网 Portal）
     → 重定向至 IdP（ADFS / Okta / Ping）
     → IdP 认证后签发 XML 断言（含签名 + 可选加密）
     → 浏览器 POST 回 SP 的 ACS 端点
     → SP 验签、解析 Attribute → 建立本地会话
```

**关键差异对比（SAML vs OIDC）：**

| 维度 | SAML 2.0 | OIDC |
| --- | --- | --- |
| 数据格式 | XML | **JSON / JWT** |
| 传输方式 | HTTP POST / Redirect 绑定 | 标准 HTTP + JSON API |
| 移动端 / SPA 支持 | 差（依赖浏览器 POST） | **好** |
| 部署复杂度 | 高（证书、元数据、端点、Attribute 映射） | 低（Discovery 自动发现） |
| 企业存量系统支持 | **极好**（二十年积累） | 逐步提升 |
| 属性扩展灵活性 | 强（任意 AttributeStatement） | 较强（自定义 claim） |
| 新项目推荐度 | 仅在已有 IdP 强制要求时 | **优先** |

**安全要点：**

- **必须验证 XML 签名**，并检查断言未被篡改；历史上多次出现 XML Signature Wrapping 类签名验证绕过漏洞
- 防止 **XXE**（XML 外部实体注入）：禁用外部实体解析，这是 SAML 库的经典高危项
- 校验 `AudienceRestriction`、`NotOnOrAfter`、`InResponseTo`，防止断言重放与跨 SP 冒用
- 证书轮换需有重叠期，元数据须从可信通道获取

**适用场景：** 企业内网 SSO、对接客户既有 IdP（ADFS / Ping / Okta）、采购合同明确要求 SAML 的合规场景。

### 3.6 API Key — 最简单的机器凭证

**形态**：一串高熵随机字符串，通过 Header 传递。

```http
GET /api/v1/data HTTP/1.1
X-API-Key: sk_live_9f2e...
```

**优点：** 极简单、无握手、无状态、天然适合脚本与 CI/CD、便于按 key 做计量与限流。

**缺点（安全上的先天不足）：**

| 问题 | 说明 |
| --- | --- |
| **无内置过期机制** | 一旦泄漏长期有效，只能靠人工轮换制度 |
| **不属于任何标准** | 无 `iss` / `aud` / `scope`，无法表达细粒度权限与受众限制 |
| **易误提交到代码库** | 公开仓库泄漏频繁，需 secret scanning 兜底 |
| **等价于明文凭据** | 无法像私钥那样做 proof-of-possession，拿到即用 |
| **缺乏用户级身份上下文** | 通常只表达「属于某调用方」，而非「谁在操作」 |

**安全加固实践：**

- 只通过 Header 传递，**绝不走 URL Query**（会被日志、Referer、浏览器历史记录）
- 存储时**哈希入库**（与密码同等对待），展示时只显示前缀（`sk_live_9f2e...abcd`）
- 支持 key 的**作用域限制**（只读 / 限 IP / 限端点子集）、**有效期**、**最后使用时间**
- 提供自助轮换与即时吊销能力，并保留审计
- 前缀标识环境（`sk_live_` / `sk_test_`），便于泄漏时快速识别与扫描

**适用场景：** 机器对机器集成、开放平台的开发者凭据、Webhook 签名校验、CI 环境变量。

### 3.7 基于证书的认证（mTLS / X.509）

**单向 TLS vs 双向 TLS：**

```
单向 TLS（HTTPS）：只有客户端验证服务端 —— 「我确认你是银行」
双向 TLS（mTLS）：双方互验证书  ──────「我确认你是银行，你也确认我是张三的设备」
```

**为什么 mTLS 在服务端场景强势：**

- **身份内置于连接层**：握手完成即完成认证，无需应用层传递凭证
- **私钥不出设备**：证书认证依赖私钥签名握手数据（proof-of-possession），**中间人拿到证书文件也无法冒用**
- **天然抗钓鱼**：没有可被骗走的「密码」，主机名由证书绑定
- **无需共享密钥**：服务端只需信任 CA 公钥

**代价：**

| 挑战 | 说明 |
| --- | --- |
| **证书生命周期管理复杂** | 签发、分发、轮换、吊销（CRL / OCSP）是一整套 PKI 工程 |
| **过期是常见故障源** | 短时效证书（小时级）必须配合自动化续期 |
| 客户端集成门槛高 | 移动端 / 浏览器场景不友好 |
| 吊销检查有延迟与开销 | OCSP stapling 可缓解 |

**现代演进：**

- **SPIFFE / SPIRE**：为工作负载签发短时效、自动轮换的 X.509 SVID，把「服务身份」标准化
- **服务网格（Istio / Linkerd）**：把 mTLS 下沉到 sidecar，应用代码零改造即获全链路加密与强身份认证；这是**零信任网络**（BeyondCorp / BeyondProd）的基石之一
- **RFC 8705**：OAuth 2.0 的 mTLS 客户端认证 + 证书绑定令牌，在应用层获得 mTLS 的安全收益

**适用场景：** 内部微服务、服务网格、金融 / 支付接口、IoT 设备接入、B2B 高价值专线对接。

---

### 3.8 多因素认证（MFA / 2FA）

| 方式 | 因子 | 安全性 | 抗钓鱼 | 体验 | 备注 |
| --- | --- | --- | --- | --- | --- |
| **SMS 验证码** | 持有 | **低** | ❌ | 好 | SIM 交换攻击、信令网劫持；NIST 已限制其作为独立第二因子，应视为过渡方案 |
| **TOTP / HOTP**（RFC 6238 / 4226） | 持有 | 中高 | ❌ | 中 | Authenticator App 生成 30s 验证码；弱点在于用户会被钓鱼站点骗走验证码 |
| **推送确认** | 持有 | 中高 | ⚠️ | 好 | 需防「疲劳推送攻击」（连续请求直到用户误点）→ 加数字匹配 |
| **Email 验证码** | 持有（邮箱） | 低中 | ❌ | 好 | 邮箱自身的安全水平即上限，一般不作为强因子 |
| **WebAuthn / FIDO2 / Passkey** | 持有 + 固有 | **最高** | ✅ | **最好** | 见下 |
| **硬件 OTP Key** | 持有 | 高 | ⚠️ | 中 | 物理设备按键输出 |
| **备份码** | 持有 | 中 | — | — | MFA 兜底恢复手段，需一次性使用 + 哈希存储 |

**WebAuthn / Passkey 为什么是终局形态：**

```
注册：服务器生成 challenge → 浏览器调用 navigator.credentials.create()
     → 认证器在设备内生成密钥对，私钥永不出 Secure Enclave / TPM
     → 上送公钥 + 凭证 ID 存服务器

登录：服务器生成 challenge → 认证器用私钥对 challenge + origin 签名
     → 服务器用公钥验签
```

- **抗钓鱼是内建的**：认证器校验 `origin`，钓鱼域名下签名必然不匹配，物理上无法被诱导
- **无共享密钥泄漏面**：服务器只存公钥，数据库泄漏不等于身份失守
- **无密码**：同时消除密码重用、撞库、暴力破解、服务端哈希存储等一整类问题
- **Passkey 的云同步**（iCloud 钥匙串 / Google 密码管理器）解决了跨设备可用性，代价是引入依赖厂商账户的新信任面

**适用场景：** MFA 应作为所有含敏感数据的系统的默认要求；Passkey 适合面向大众的 ToC 产品，WebAuthn + 硬件 Key 适合 ToB 高安全场景。

### 3.9 其他值得了解的形式

| 形式 | 说明 | 评价 |
| --- | --- | --- |
| **Kerberos** | 域内认证，靠票据（TGT / Service Ticket）与对称密钥，Windows AD 的地基 | 企业内网透明 SSO 极佳；跨公网 / 跨平台差 |
| **Basic Auth** | `Authorization: Basic base64(user:pass)` | Base64 非加密；**必须配 TLS**；仅适合内网或作为网关前的粗筛 |
| **Magic Link / Email OTP** | 邮件发送一次性登录链接 | 体验好、无密码负担；依赖邮箱安全，SMTP 延迟影响可用性 |
| **Digest Auth** | Basic 的哈希改良版 | 基本被淘汰 |
| **JWT Bearer Grant**（RFC 7523） | 用一个已认证的 JWT 换取另一个令牌 | 服务链路中的令牌交换与身份映射 |
| **Token Exchange**（RFC 8693） | 令牌换令牌（降权、换受众） | 微服务「模拟」与「降级」场景的标准做法 |
| **SCIM**（RFC 7643 / 7644） | 用户生命周期同步（开通 / 停用） | 常与 SSO 配套；**离职即停权**才是企业 SSO 的真正价值 |
| **网关代认证** | 反向代理 / API Gateway 统一认证后向后端注入可信头 | 见 4.6 的陷阱说明 |

## 第四部分 鉴权（授权）的实现形式

### 4.1 五种主流模型

```
粒度由粗到细、复杂度由低到高

ACL ──────→ RBAC ──────→ ABAC ──────→ ReBAC ──────→ PBAC
谁对这个      谁扮演什么     谁 + 什么环境   谁与谁的      策略即代码
资源能做什么   角色能做什么   下能做什么     关系决定了什么  集中决策多点执行
```

#### 4.1.1 ACL（Access Control List，访问控制列表）

资源上挂一张「主体 → 权限」清单（文件系统 rwx、S3 Bucket Policy）。

- ✅ 直观、对单一资源的控制精确
- ❌ 主体 / 资源数量增长后呈 **O(n×m)** 膨胀，无法批量管理
- 适用：文件系统、少量共享资源

#### 4.1.2 RBAC（Role-Based，基于角色）

**最广泛落地的模型。** 引入 Role 中间层解耦用户与权限：

```
User ──(多对多)──> Role ──(多对多)──> Permission ──> Resource:Action
```

权限不再直接赋予用户，而赋予角色；用户通过担任角色获得权限。变更某人权限只需改 membership。

- ✅ 易理解、易审计、天然契合组织架构，满足绝大多数业务
- ❌ **角色爆炸**：细微差异就得新建角色（`admin` / `admin_finance` / `admin_finance_readonly`…）
- ❌ 难以表达动态条件（「工作日 9–18 点」「仅本人创建的数据」）
- 适用：企业后台、SaaS 多租户的基础权限骨架

#### 4.1.3 ABAC（Attribute-Based，基于属性）

用**主体属性 + 资源属性 + 环境属性 + 动作**的策略表达式判定：

```
允许 IF  user.department == resource.owner_department
     AND request.time BETWEEN 09:00 AND 18:00
     AND user.clearance >= resource.classification
     AND request.ip IN trusted_ranges
```

- ✅ 表达力极强，一条策略覆盖无数情况；新场景**加策略不加角色**
- ❌ 属性基础设施（治理、同步、可信度）成本高；策略复杂后难调试、难预测
- 代表：XACML（重）、AWS IAM Policy（实践中的主流形态）
- 适用：云平台、合规驱动的跨组织数据共享、细粒度条件密集的场景

#### 4.1.4 ReBAC（Relationship-Based，基于关系）

权限由**实体间的关系图**推导：

```
doc:report ──parent──> folder:finance ──parent──> org:acme
user:alice ──member──> group:eng ──viewer──> folder:finance
⇒ alice 是否有 report 的 viewer 权限？沿关系图可达性计算
```

- ✅ 完美适配社交网络、协作文档、层级组织这类天然图结构
- ❌ 图查询性能是核心挑战，需专门的缓存与一致性模型（zookie / zedtoken）
- 代表：Google Zanzibar（及其开源实现 SpiceDB、OpenFGA）、GitHub 权限、Notion 共享
- 适用：协作产品、多级组织架构、「所有权继承自父容器」的场景

#### 4.1.5 PBAC / Policy-as-Code

把判定逻辑从代码中抽出为**独立策略语言**，由策略引擎统一决策：

| 项目 | 语言 | 特点 |
| --- | --- | --- |
| **OPA**（Open Policy Agent） | Rego | CNCF 毕业项目，事实标准；K8s Admission、Envoy、微服务皆可接入 |
| **Cedar** | Cedar | AWS 出品，形式化验证友好，可读性强 |
| **Casbin** | 模型 DSL | 多语言支持，同时涵盖 ACL / RBAC / ABAC / ReBAC |

- ✅ 策略可版本化、可测试、可独立审计；应用与策略解耦
- ❌ 引入新语言的学习成本与额外决策延迟

### 4.2 模型选型对照

| 维度 | ACL | RBAC | ABAC | ReBAC | PBAC |
| --- | --- | --- | --- | --- | --- |
| 表达力 | 低 | 中 | 高 | 高（图关系） | 最高 |
| 实现复杂度 | 低 | 中 | 高 | 高 | 中高 |
| 角色爆炸风险 | — | **高** | 低 | 低 | 低 |
| 审计可读性 | 好 | **最好** | 中 | 中 | 中 |
| 性能特征 | O(1) | O(1) | 取决于表达式 | 图遍历 | 取决于策略 |
| 起步建议 | 少量共享资源 | **默认选择** | 条件复杂时叠加 | 协作类场景 | 多服务统一管控 |

> **实践建议**：绝大多数系统**从 RBAC 起步**已足够；当出现「角色数量失控」或「需要动态条件」时，再向 RBAC + ABAC 混合或 PBAC 演进。**不要一上来就上 ABAC**——表达力的代价是治理负担。

### 4.3 鉴权的位置：策略执行点 vs 决策点

```
请求 → PEP（Policy Enforcement Point，中间件 / 网关 / SDK）
         │  提取 subject / action / resource / context
         ↓
       PDP（Policy Decision Point，策略引擎）←── PIP（属性源：DB / IdP / LDAP）
         │  allow / deny
         ↓
       PEP 执行结果 → 记录审计
```

把 PDP 独立出来（尤其在微服务中）的好处：策略一处变更全局生效，且判定逻辑可被单独测试与审计。

### 4.4 OAuth Scope — 授权框架里的粗粒度鉴权

Scope 是「用户授予第三方应用的能力边界」，本质是**面向委派场景的粗粒度 ABAC**：

- 应由服务端**最小化授予**，并按资源敏感度分层（`read:profile` vs `write:billing`）
- Scope 检查应在资源服务器端做，**不能只在网关**（否则绕过网关的内部调用即失守）
- Scope ≠ 业务权限。Scope 决定「这个 token 能碰哪类 API」，业务权限决定「这个用户能碰哪条数据」——**两层都要查**

### 4.5 数据层兜底：RLS

**Row Level Security**（PostgreSQL RLS / Snowflake / BigQuery Policy Tags）把权限下推到数据库：即使上层代码有漏洞，多租户数据也不会互相泄漏。这是**纵深防御**在多租户场景的关键一环，建议始终开启。

### 4.6 网关代认证的陷阱

反向代理 / API Gateway 统一认证后向后端注入 `X-User-Id` 头，是常见的简化手段，但有严格前提：

1. **必须剥离外部传入的同名头**（否则客户端可伪造 `X-User-Id: admin` 直穿）
2. 后端服务**不可从公网直连**，网络层要强制流量必经网关
3. 内部通信应加密（mTLS），防止中间节点注入
4. 内部调用（定时任务、微服务互调）需有独立的身份机制，不能复用「无用户」的默认放行

## 第五部分 横向对比总表

### 5.1 认证方式综合对比

| 方式 | 状态性 | 主要主体 | 典型场景 | 核心优点 | 主要缺点 / 风险 | 吊销能力 |
| --- | --- | --- | --- | --- | --- | --- |
| **Session-Cookie** | 有状态 | 人类用户 | 传统 Web、内部后台 | 可即时吊销、XSS 免疫、实现简单 | 分布式需共享存储；CSRF 风险；跨域受限 | **强** |
| **JWT（自包含）** | 无状态 | 用户 / 服务 | SPA、移动、微服务 | 无回源、易跨服务传递、性能好 | 不能即时吊销；Payload 明文；令牌体积大 | **弱** |
| **不透明令牌** | 有状态 | 用户 / 服务 | 需强管控的 API | 可即时吊销、可含丰富元数据、体积小 | 每次校验需回源 | **强** |
| **OAuth 2.0** | — | 第三方客户端 | 开放平台、委派授权 | 用户不把密码交给第三方、scope 可控 | **是授权不是认证**；实现复杂；重定向劫持风险 | 视令牌类型 |
| **OIDC** | — | 人类用户 | 现代 SSO、社交登录 | 在 OAuth 上标准化身份；Discovery 简化对接 | 依赖外部 IdP 可用性；需正确校验 nonce / iss / aud | 视 IdP |
| **SAML 2.0** | — | 企业员工 | 企业内网 SSO | 存量支持最好、属性扩展灵活 | XML 复杂、XXE 风险、移动端差、配置繁琐 | 视 IdP |
| **API Key** | 无状态 | 机器 / 开发者 | 开放 API、CI/CD | 极简单、适合脚本与计量 | 无标准、易泄漏代码库、难表达细粒度权限 | 中（需自建） |
| **mTLS / 证书** | 无状态（依赖 PKI） | 服务 / 设备 | 微服务、金融、IoT | 抗钓鱼内建、proof-of-possession、零信任基石 | PKI 运维复杂；过期易故障；移动端不友好 | **强**（CRL / OCSP） |
| **TOTP / 推送** | 作为第二因子 | 人类用户 | 通用 MFA | 显著提升安全性、部署轻量 | TOTP 可被钓鱼套走；推送面临疲劳攻击 | — |
| **WebAuthn / Passkey** | 无状态（公私钥） | 人类用户 | 面向大众 / 高安全 | **最强**：抗钓鱼、无共享密钥、体验最好 | 设备丢失需恢复流程；跨设备依赖云同步 | 强（删凭证） |
| **Kerberos** | 有状态（KDC） | 企业员工 | Windows 域内网 | 域内透明 SSO、体验极佳 | 依赖 KDC 高可用；跨公网差；时钟敏感 | 中 |
| **Basic Auth** | 每次携带 | 机器 / 内网 | 网关粗筛、内网工具 | 实现成本几乎为零 | 凭据每次传输、无过期、强依赖 TLS | 中 |

### 5.2 鉴权模型综合对比

| 模型 | 决策依据 | 表达力 | 运维成本 | 适用规模 | 代表实现 |
| --- | --- | --- | --- | --- | --- |
| ACL | 资源上的主体清单 | 低 | 低 | 小（单资源） | 文件系统、S3 Policy |
| RBAC | 角色 | 中 | 中 | 中大（主流） | Spring Security、Casbin |
| ABAC | 属性 + 策略表达式 | 高 | 高 | 大（合规密集） | XACML、AWS IAM |
| ReBAC | 关系图可达性 | 高 | 高 | 大（协作类） | Zanzibar、SpiceDB、OpenFGA |
| PBAC | 外部策略引擎 | 最高 | 中高 | 大（多服务） | OPA、Cedar、Casbin |

### 5.3 按需求快速筛选

| 如果你需要… | 首选 |
| --- | --- |
| 最快上线一个后台管理 | Session-Cookie + HTTPS |
| 前后端分离 + 移动端 | OIDC（或自建 JWT）+ Refresh Token 轮换 |
| 「踢下线」能力 | Session 或不透明令牌，**不要纯 JWT** |
| 每秒百万次 API 校验 | JWT 本地验签（接受吊销延迟）或 边缘网关缓存 introspection |
| 用户用微信 / Google 登录 | OIDC |
| 对接客户公司的 ADFS | SAML 2.0 |
| 开放 API 给外部开发者 | OAuth 2.0 + API Key 双层 |
| 服务之间互相调用 | mTLS（服务网格）+ 短时效 JWT / Token Exchange |
| 根治钓鱼 | WebAuthn / Passkey |
| 金融级合规 | mTLS + MFA（AAL3）+ 硬件 Key + 全链路审计 |

## 第六部分 场景选型指南

### 6.1 场景 × 推荐组合

| 场景 | 推荐认证 | 推荐鉴权 | 关键理由 |
| --- | --- | --- | --- |
| **个人本地工具 / 单机自用** | 不暴露公网，绑定 `127.0.0.1` + 反向代理前置 Basic / SSO | 单用户，无需权限模型 | 攻击面零暴露即可，别过度设计 |
| **小团队内部 Web 工具** | Session-Cookie（Redis 存会话）+ 简单 MFA 或 OIDC | RBAC（admin / member 两级） | 上线快、可即时踢人、运维简单 |
| **ToC 移动 App / SPA** | OIDC Authorization Code + PKCE；Access（JWT、短）+ Refresh（轮换） | RBAC + 所有者校验 | PKCE 防授权码截获；轮换防 Refresh 泄漏 |
| **开放平台 / 第三方开发者** | OAuth 2.0 Authorization Code + Client Credentials | Scope + RBAC（tenant 隔离）+ RLS | Consent 页面是合法性基础；必须做多租户行级隔离 |
| **微服务集群** | 边缘网关终结外部 JWT → 内部 mTLS + 短时效服务令牌 | PBAC（OPA / Cedar）集中决策 | 双区认证；策略一处变更全局生效 |
| **企业内网 SSO** | SAML 2.0（对接存量 IdP）或 OIDC（新建） | RBAC + SCIM 自动开通 / 停用 | **离职即停权**才是 SSO 的真正价值 |
| **机器对机器 / ETL / CI** | Client Credentials 或 API Key（短周期、可轮换） | Scope 最小化 + IP allowlist | 凭据绝不能长期不变 |
| **IoT 设备接入** | mTLS 设备证书 + 自动轮换 | 按设备身份的最小 scope | 设备易被物理接触，需远程吊销能力 |
| **金融 / 医疗 / 政务** | mTLS + Passkey / 硬件 Key（AAL2~AAL3）+ 全链路审计 | ABAC 或 PBAC + RLS | 合规要求可举证、可追溯，必须支持按数据分类分级 |

### 6.2 场景化演进路径（不要一步到位）

```
阶段一（0 → 1）：单点可用
   Session-Cookie + HTTPS + 密码哈希（Argon2id）
   └ 目标：能安全地让第二个人用上

阶段二（1 → 10）：多人协作
   抽出 Principal 概念 + RBAC 两级角色 + 审计日志
   └ 目标：可管理、可追责

阶段三（10 → 100）：外部接入
   OIDC 联邦登录 + SCIM 同步 + Refresh Token 轮换
   └ 目标：接入企业 IdP，降低账号治理成本

阶段四（100 → N）：多租户与合规
   PBAC 策略引擎 + RLS + MFA 强制 + 密钥托管（KMS / HSM）
   └ 目标：可举证、可审计、可横向扩展
```

> **关键忠告**：认证鉴权的复杂度应与**威胁模型**匹配，而非与技术潮流匹配。一个跑在 `127.0.0.1` 的个人工具不需要 OAuth；而一个面向公众的多租户 SaaS 却用「客户端自选 thread_id」则是重大缺陷。

### 6.3 技术选型的五个判断维度

| 维度 | 需要回答的问题 |
| --- | --- |
| **主体类型** | 是人类用户、第三方应用，还是服务 / 设备？（决定认证方式的分岔） |
| **状态性容忍度** | 能否接受「吊销延迟」（无状态）还是必须「即时生效」（有状态）？ |
| **信任边界** | 校验方与签发方是否同一实体？跨组织吗？ |
| **合规要求** | 是否需满足 NIST AAL / PCI-DSS / 等保 / GDPR 的具体条款？ |
| **运维能力** | 团队能否承担 PKI、密钥轮换、策略引擎的运维成本？ |

## 第七部分 通用安全考量清单

> 无论选哪种方案，以下条目都适用。这是「方案无关」的底线清单。

### 7.1 凭据与密钥

- **绝不存储明文密码**。使用专为密码设计的慢哈希：**Argon2id**（首选）、scrypt、bcrypt；**禁用** MD5 / SHA-1 / 单轮 SHA-256
- 每个用户使用独立随机 salt；哈希参数（内存 / 迭代次数）应可随硬件升级而演进
- 密钥与签名私钥必须托管在 **KMS / HSM / Secrets Manager**，绝不写进代码或配置文件入库
- 密钥必须支持**轮换**，且轮换期间新旧并存（通过 `kid` 或版本号区分），轮换后旧密钥保留足够长以覆盖长时效令牌

### 7.2 传输与存储

- 全站 HTTPS，启用 **HSTS**；内部通信也应加密（mTLS）
- 令牌 / 会话 ID 只在 HTTPS 下传输，Cookie 加 `Secure`
- 敏感字段落库前加密（如手机号、身份证）；日志中**不得打印令牌与密码**

### 7.3 令牌专属风险

| 风险 | 说明 | 防护 |
| --- | --- | --- |
| **算法混淆攻击** | 攻击者把 `alg` 改为 `none`，或用公钥当 HMAC 密钥（RS256 → HS256） | **服务端固定允许的算法白名单**，绝不信任 Header 里的 `alg` |
| **未校验关键 claim** | 只验签不验 `aud` / `iss` / `exp`，令牌可跨服务复用 | 逐项校验，`aud` 必须匹配本服务 |
| **重放攻击** | 令牌被中间人截获后重复使用 | 短 TTL、`jti` 去重、nonce（OIDC）、TLS 保证传输机密 |
| **时钟偏移** | `exp` / `nbf` 判定错误 | 允许 30~60s leeway + 全链路 NTP |
| **令牌泄漏无感知** | 无法察觉已被盗用 | 绑定设备指纹 / IP；监控异常地理与并发；Refresh Token 重放检测 |

### 7.4 登录流程专属风险

- **暴力破解**：失败计数 + 指数退避 + 账户临时锁定 + CAPTCHA；对同一 IP 与同一账号双向限流
- **用户枚举**：登录失败提示保持模糊（「用户名或密码错误」），注册 / 找回密码接口也不要区分「用户不存在」与「密码错误」
- **CSRF**：`SameSite` Cookie + CSRF Token 双重防护；CSRF Token 需与会话绑定且一次性
- **会话固定**：登录成功后必须重新生成会话标识
- **开放重定向**：登录后的跳转目标必须校验白名单，不能直接使用请求参数
- **OAuth 重定向 URI**：**必须精确匹配**注册值，禁止通配符与子路径放宽（这是 OAuth 最常被利用的漏洞）

### 7.5 运营与审计

- **全量审计日志**：登录成功 / 失败、权限变更、敏感操作、令牌签发与吊销；日志需防篡改与集中存储
- **异常检测**：不可能旅行（短时间内跨洲登录）、异常时段、新设备告警
- **最小权限原则**：默认拒绝（deny by default），显式授予；定期做权限回收审查
- **纵深防御**：认证在网关、鉴权在服务、隔离在数据层（RLS），任何单层失守都不应导致全面失守
- **依赖与合规基线**：关注 OWASP ASVS 的认证与授权章节、NIST SP 800-63 系列、OAuth 2.0 安全最佳实践（RFC 9700 / JWT BCP RFC 8725）

### 7.6 反模式清单（看到就要警惕）

| 反模式 | 为什么危险 |
| --- | --- |
| 用 OAuth 2.0 做登录 | 拿到任意 token 即可冒充；必须用 OIDC |
| 客户端自行生成 / 指定资源 ID | 可预测 ID 即越权读写的入口 |
| 只在网关做鉴权 | 绕过网关的内部调用或直连端口即完全失守 |
| 把敏感数据放进 JWT Payload | Payload 是明文 Base64，等于公开 |
| Refresh Token 永不轮换 | 一次泄漏 = 永久访问权 |
| 用「有没有登录」代替「有没有权限」 | 认证 ≠ 鉴权，越权典型成因 |
| 明文或可逆加密存密码 | 库泄漏即全员失守 |
| 生产环境用 `alg: none` 或固定密钥 | 令牌可任意伪造 |

## 第八部分 回到本项目：选型建议

结合 `功能完整度分析与缺失功能清单.md` 中的 #1 号 P0 缺口，给出针对性的落地思路（**不涉及具体实现代码**）。

### 8.1 当前的真实威胁模型

| 事实 | 含义 |
| --- | --- |
| 默认绑定 `127.0.0.1`（`config.py:197`） | 默认仅本机可访问，公网威胁为零 |
| `application/thread_service.py:79-91` 注释自陈「端点当前没有鉴权」 | 一旦改绑 `0.0.0.0` 或经反向代理暴露，即全面失守 |
| 会话 ID 由服务端 `uuid4().hex` 生成 | 不可预测，这是目前唯一的「隐形防线」 |
| `thread_meta` 表无用户维度 | 无法表达归属，多人共用时所有人看到同一份会话清单 |
| HITL 审批决策不落库 | 审计链缺失，安全卖点无法自证 |

**结论**：当前处于「默认安全但零治理」的状态。**风险不在于已被攻破，而在于无法安全地扩大使用范围。**

### 8.2 分阶段建议

#### 阶段一：最小改动，堵住外暴露（若必须分享给他人使用）

- 保持 `127.0.0.1` 绑定，通过**反向代理**（Nginx / Caddy / Cloudflare Tunnel）暴露，认证完全交给代理层
- 若无条件必须直连，则至少启用一层**静态 API Key / Basic Auth**（仅在 TLS 之下）
- 配置校验：启动时若检测到 `HOST` 非回环地址且无任何认证配置，**应显式拒绝启动或打醒目告警**——静默允许是最危险的默认值

#### 阶段二：引入用户维度（真正的改造起点）

- 数据层：为 `thread_meta` 增加 `user_id` 字段，并在所有查询中强制带上该条件（**不能只靠应用层过滤，建议同时启用 SQLite / 目标库的行级隔离手段作为兜底**）
- 服务层：`ThreadService` / `RunService` 的每个方法都接受 `Principal` 参数，权限判定收敛到一处，避免散落到路由层
- 会话 ID 继续由服务端生成（该属性必须保留，`thread_service.py:84-87` 的注释已正确论证了理由）

#### 阶段三：认证方案选择（按推荐度排序）

| 方案 | 适用前提 | 理由 |
| --- | --- | --- |
| **① 反向代理 + OIDC（推荐）** | 有企业 / 第三方 IdP | 改动量最小：应用只需信任代理注入的身份头，**且必须剥离外部同名头**（见 4.6）；无需自建密码体系与找回流程 |
| **② 自建 Session-Cookie** | 无 IdP，用户量小 | 实现成本可控、可即时吊销、XSS 免疫；需配套 Argon2id 密码哈希、CSRF 防护、登录限流 |
| **③ API Key（仅机器调用）** | 只面向脚本 / CI | 注意哈希存储、作用域限制与轮换；**不要用它做人类用户的登录方式** |
| **④ 自建 JWT** | 需跨服务传递身份 | 本项目当前无需此复杂度，**不推荐作为首选**——JWT 的吊销难题在没有多服务架构时纯属自找麻烦 |

> 特别提示：本项目 SSE 走的是 `fetch + ReadableStream`（`interfaces/web/static/app.js:191-214`）而非原生 `EventSource`，因此**可以携带自定义认证头**。这是当前架构的一个隐性优势——若用的是 `EventSource`，流式端点将无法附加 `Authorization` 头，认证设计会被迫改用 Cookie 或 URL 参数（后者会泄漏到日志）。

#### 阶段四：鉴权模型

- 起步用 **RBAC 两级**（`admin` / `member`）即可覆盖绝大多数场景
- 核心规则是**所有者校验**：`thread.user_id == principal.id`，本质是 ReBAC 的最小形态
- 不要一上来就引入 ABAC 或策略引擎——当前业务不存在需要它的复杂度

#### 阶段五：与审计补齐

- 认证与审计必须**同期落地**：只做认证不做审计，等于能拦住但说不清
- 审计应记录：登录事件、会话创建 / 删除、HITL 审批决策（四类决策各自的决策者与时间）、权限拒绝事件
- 这恰好与清单中的 #3 号 P0 项重合，建议二者合并为一个迭代交付

### 8.3 一句话总结

> **本项目最合理的认证路径是「复用外部 IdP，不自建密码体系」**：应用只做「信任上游注入的身份 + 按所有者鉴权 + 全量审计」这三件事，把密码学与凭据治理交给专业的 IdP。这样既能在几天内补上 P0 缺口，也不会把 PKI、密钥轮换、MFA、找回密码这些长期负担引入一个目前只有几千行的代码库。
