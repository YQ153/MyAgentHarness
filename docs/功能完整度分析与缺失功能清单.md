## 二、三维度缺口分析

### 维度 1：用户需求视角（我想做的事做不了）

1. ✅ **能停了**：`POST /api/threads/{id}/stop` + 前端停止按钮 + 协作式取消；T7 补上取消后
   2 秒内整棵进程树消失的进程层确认。
2. 🟡 **部分能改**：会话**标题**可重命名（T10）；**消息本身仍不可编辑、不可重新生成、
   不能从历史某轮分叉**——不满意只能重开会话。
3. ⬜ **仍不能看**：工具结果只有截断预览（`application/event_translator.py`），前端仅追加
   一行「(输出已截断)」，无「查看完整输出」入口；Web 端**没有工作区文件面板**——
   而 `workspace/` 里确实已经躺着 Agent 产出的文件（如 `react-vite-app/`），用户却看不见。
4. ⬜ **不能传**：输入仅限纯文本，无文件上传 / 图片 / 多模态，无附件机制。
5. 🟡 **只能按标题搜**（T10）：`GET /api/threads?query=` 支持标题搜索，侧栏有搜索框与
   「含已归档」开关；**仍缺**正文检索（正文在检查点 BLOB 里，需另建索引）。
6. ⬜ **不能带走**：无导出（Markdown / JSON）、无分享链接、无导入。
7. 🟡 **能换模型，不能换人格**：模型下拉已有多项可选（T5）；**temperature 等参数仍只藏在
   `.env`**，系统提示词仍硬编码于 `agent/profiles.py`，无自定义人格 / 角色模板。

### 维度 2：业务流程视角（上线会断在哪一环）

1. ✅ **身份与归属已就位**：`thread_meta.owner_id` + 角色权限模型（viewer / member / admin）；
   跨用户读写会话会被 403 拦下，管理员是显式的运维兜底路径。
2. ✅ **审计已闭环**：审批决策、工具执行、会话增删改、记忆删除、越权拒绝全部落库，
   带请求来源（IP / UA）与归档保留策略。
3. 🟡 **计量完成一半**（T6）：每轮 token 用量可观测——`usage_log` 落库 + `GET /api/usage`
   按用户 / 会话 / 时间窗聚合 + 前端与 CLI 展示本轮消耗；**仍缺**费用估算与用量配额，
   成本控制目前只有 `MAX_MODEL_CALLS_PER_RUN=60` 这一道粗粒度护栏。
4. 🟡 **运维接口完成一半**（T4）：`/health`（进程存活）、`/ready`（DB + 默认模型静态自检）、
   `/metrics`（运行数 / 挂起数 / 审计计数 / 治理计数）已可用；**仍缺** trace_id、
   结构化日志与链路追踪集成。
5. 🟡 **中断兜底完成一半**：T7 补上中断 TTL（超期作废、拒绝过期审批）与运行超时强制取消；
   **仍缺**超期前的提醒与「谁该审批」的通知通道。
6. 🟡 **运行治理完成一半**：超时强制取消、HITL 挂起 TTL、进程树回收已交付；
   **仍缺**全局并发上限、按用户限流、优先级队列——目前只有 per-thread 单槽互斥
   （`RunService._acquire_run_slot`）。认证端点有 IP 级限流，但那与「按用户限运行」不是一回事。
7. 🟡 **数据生命周期完成一半**：审计归档与保留策略、会话删除时的检查点清理、
   会话归档（软删除回收站）已落地；**仍缺**数据库迁移版本管理（T10 为 `thread_meta`
   手写了两条 `ALTER TABLE`，但没有通用迁移框架）与**孤儿检查点清理**
   （审计有定期清理任务，检查点没有——只能随会话删除逐条清）。

### 维度 3：竞品对比视角（别人都有什么）

对标 Claude Code / Cursor / ChatGPT / OpenHands：

| 竞品标配 | 本项目现状 | 状态 |
| --- | --- | --- |

| 用量面板与费用统计 | 每轮用量 + `/api/usage` 聚合可用 | 🟡 **仍缺**费用估算与配额：个人无法控本，团队无法核算 |
| 长期记忆（跨会话） | SQLite Store 持久化 + 命名空间按主体隔离 + 面板查看 / 删除 | ✅ 重启不丢且自查自纠；**仍缺**跨主体管理入口（管理员也只看自己的） |
| 技能 / 插件市场与自定义 Agent | `workspace/skills/` 为空目录，无管理入口 | ⬜ 架构备好但没内容，可复用资产无法沉淀 |
| 会话搜索 / 归档 / 导出 | 标题搜索、重命名、归档（可恢复）已交付；正文检索与导出 / 导入未做 | 🟡 历史资产可整理，但还带不走 |
| 容器化部署与 CI | 无 Dockerfile / compose / CI | ⬜ 交付靠手搓、无自动质量门禁。**测试网已建成**（605 项，T1 → T10 累积），缺的只是流水线 |

## 五、结论

**内核与安全设计是超额完成的**（分层、护栏、沙箱、HITL 都做到了生产级思考）。经过 T1 → T10，
原先「几乎为零」的那一侧已经补上：**身份、控制、可见性、可运维、可计量、可追溯**全部就位，
Sprint 1~4 的门禁全部达成。

当前的短板从「缺基础设施」变成了两类具体问题：

1. **能力边界**：信息获取（⑤ 检索）、产物可见性（⑬ 文件面板）、交互闭环（⑨ 重生成）
   ——这三项决定 Agent 能解什么任务、用户敢不敢信结果。
2. **生产化收尾**：故障转移、费用配额、链路追踪、并发治理、容器化与 CI
   ——没有它们，系统能自用但不好交付给团队。

建议的下一步：从 **⑤ 联网检索** 开始。它既是能力空白里最影响任务范围的一项，
又是对 T8「配置化扩展」最直接的验收——如果接一个搜索工具仍然要改内核，
说明 T8 的设计没做到位，那才是更需要优先修的问题。

## 附：本次校准中发现的新问题

在逐项对照代码核对时发现两处此前未记录的问题，均与功能完整度无关，故单列：

1. **`AppConfig.__repr__` 会输出密钥**：`deepseek_api_key` 等字段参与默认 `repr`，
   任何 `repr(config)`、pytest 断言失败输出、异常上报都会把真实密钥带出去
   （已在一次 pytest 失败输出中实际观察到）。建议用 `Field(repr=False)` 收口。
2. **`docs/` 下三份历史文档仍引用已移除的符号**：`分层架构评估与重构方案.md`、
   `分层架构重构实施记录.md`、`认证与鉴权技术方案.md` 中的代码片段仍写着
   `build_store` / `InMemoryStore`。它们记录的是当时的方案，按「历史记录」保留，
   但读者若照抄会拿到已经不存在的东西——需要时再加一句醒目的「本文档为历史快照」。
