> 分析范围：`agent/` `application/` `interfaces/` `runtime/` `llm/` `config.py` `main.py` 全量走查

## 一、现状能力盘点（已实现）

| 分层 | 已实现能力 | 关键证据 |
| --- | --- | --- |
| `agent/` | deepagents 单一装配点、TodoList 规划、ContextEditing 上下文裁剪、模型调用次数上限、子 Agent 委派 | `agent/graph.py:59-135`、`agent/profiles.py:46-76` |

| `runtime/` | SQLite 异步检查点、会话元数据表（标题/时间/轮数/分页）、沙箱 Tier 0（Job Object）与 Tier 1（WSL）、环境变量白名单 | `runtime/checkpointer.py`、`runtime/thread_store.py`、`runtime/sandbox/` |
| `application/` | 会话编排、运行编排、LangGraph 事件翻译器、HITL 编解码（approve/edit/reject/respond）、模型目录、ThreadBusy 互斥 | `application/*.py` 全部 10 个模块 |

**总体判断：** 这是一个完成度很高的「单机单用户 Agent 内核骨架」，但停在「能跑通」与「能交付」之间——内核、安全、分层做到了生产级思考，而「人能用好、能运维、能扩展」的外围模块基本为空白。

## 二、三维度缺口分析

### 维度 1：用户需求视角（我想做的事做不了）

1. **不能停**：发送后按钮置灰为「运行中」，直到本轮结束才恢复，无「停止生成」入口；后端仅有 `/runs` 与 `/resume` 两个端点（`interfaces/web/routes.py:174-255`），一轮长任务可锁死用户数分钟。
2. **不能改**：消息不可编辑、不可重新生成、不能从历史某轮分叉；会话标题由首条消息机械截断生成（`THREAD_TITLE_MAX_CHARS=24`），无重命名。
3. **不能看**：工具结果只有 `preview` 截断文本（`application/event_translator.py:184-190`），前端仅追加一行「(输出已截断)」，无「查看完整输出」入口；Web 端无工作区文件面板，Agent 产物不可见。
4. **不能传**：输入仅限纯文本，无文件上传 / 图片 / 多模态，无附件机制。
5. **不能搜**：会话列表仅有 `limit/offset` 分页（`interfaces/web/routes.py:106-129`），无标题或内容检索。
6. **不能带走**：无导出（Markdown / JSON）、无分享链接、无导入。
7. **不能换**：模型下拉只有 DeepSeek 一项；temperature 等参数只藏在 `.env`；系统提示词硬编码于 `agent/profiles.py:27-43`，无自定义人格 / 角色模板。

### 维度 2：业务流程视角（上线会断在哪一环）

1. **无身份，流程起点缺失**：`thread_meta` 表无 `user_id` 字段；`application/thread_service.py:79-91` 注释自陈「端点当前没有鉴权」。任何人拿到 `thread_id` 即可读写删除他人会话，业务上无法定义「归属」这一基本实体。
2. **无审计，责任链断裂**：HITL 四种审批决策只在内存中流转，**不落库**——谁在何时批准了哪条命令事后不可追溯。在本项目主打 HITL 安全卖点的前提下属合规硬伤。
3. **计量仅完成一半**（T6 已落地，2026-09-17）：每轮 token 用量已可观测
   ——`usage_log` 落库 + `GET /api/usage` 按用户/会话/时间窗聚合 + 前端/CLI
   展示本轮消耗；**仍缺**费用估算与用量配额，成本控制目前只有
   `MAX_MODEL_CALLS_PER_RUN=60` 这一道粗粒度护栏。
4. **运维接口有一半**（T4 已落地，2026-09-17）：`/health`（进程存活）、
   `/ready`（DB + 默认模型配置静态自检）、`/metrics`（运行数 / 挂起数 /
   审计计数 / 治理计数）已可用；**仍缺** trace_id、结构化日志与链路追踪集成。
5. **中断兜底不足**：T7 已补上中断 TTL（超期作废、拒绝过期审批）与运行超时强制取消；**仍缺**超期前的提醒与「谁该审批」的通知通道。
6. **运行治理过半**：T7 已交付运行超时强制取消、HITL 挂起 TTL 与进程树回收
   （`stop` 即进程层确认）；**仍缺**全局并发上限、按用户限流、优先级队列
   ——目前只有 per-thread 单槽互斥（`RunService._acquire_run_slot`）。
7. **数据生命周期仅审计闭环**：T3/T4 已有审计归档与保留策略、检查点清理协程；
   **仍缺**数据库迁移 / 版本管理（靠 `CREATE TABLE IF NOT EXISTS` 隐式建表，
   见 `runtime/thread_store.py:71-81`）与软删除回收站。

### 维度 3：竞品对比视角（别人都有什么）

对标 Claude Code / Cursor / ChatGPT / OpenHands：

| 竞品标配 | 本项目现状 | 缺口性质 |
| --- | --- | --- |
| 多 Provider（OpenAI / Anthropic / 本地 Ollama） | T5 已落地：按配置条件注册（DeepSeek 恒定 + OpenAI/Anthropic/Ollama 有密钥才注册），`GET /api/models` 可查 | 已具备多供应商选择；**仍缺**运行时故障转移（当前为启动时选择，非调用失败自动切换） |
| MCP 工具生态接入 | T8 已落地：配置化 MCP server（stdio / sse / streamable_http / websocket）+ 自定义工具注册器，工具调用含来源与耗时进审计，`GET /api/tools` 可查生效清单与失败原因 | 已解除「加能力必须改内核」的约束；**仍缺**工具市场 / 一方工具包与逐用户工具授权 |
| 联网检索 / 网页抓取 | 无 | **信息获取能力为零**；沙箱网络模式为 `none`，且 `execute` 默认禁用 |
| 停止生成 / 重新生成 / 分支对话 | T2 已落地「停止生成」（端点 + 协作式取消 + 前端按钮），T7 补上超时与进程层确认；重新生成 / 分支仍无 | 交互闭环不完整（可中断，但不可回溯重来） |
| 工作区文件树与内联预览 | 无 | 产物不可见，用户无法校验结果，信任成本高 |
| 用量面板与费用统计 | 部分（T6：每轮用量 + `/api/usage` 聚合，无费用估算 / 配额） | 个人无法控本，团队无法核算 |
| 技能 / 插件市场与自定义 Agent | `workspace/skills/` 为空目录，无管理入口 | 可复用资产无法沉淀 |
| 会话搜索 / 归档 / 导出 | 无 | 历史资产不可运营 |
| 容器化部署与 CI | 无 Dockerfile / compose / CI；**测试网已建成**（378 项，T1→T7 累积） | 交付靠手搓、无自动质量门禁 |

**长期记忆问题（T9 已修）：** 此前 `runtime/store.py` 使用 `InMemoryStore`，`/memories/` 写入的内容**进程重启即丢失**，Web 端也没有查看入口；更严重的是命名空间写死为 `("memories",)`，鉴权开启后**所有用户共用一个记忆池**——B 用户的 Agent 能读到 A 用户写下的内容。现已换成 `AsyncSqliteStore`（随 `langgraph-checkpoint-sqlite` 附带，零新增依赖）、命名空间按主体收敛（`("memories", <user_id>)`），并提供 `GET/DELETE /api/memories` 与前端记忆面板。

## 三、缺失功能清单与优先级排序

优先级定义：

- **P0** = 安全红线或可用性阻塞（不做即不可交付）
- **P1** = 核心体验缺口（竞品标配，不做即明显落后）
- **P2** = 差异化增强
- **P3** = 锦上添花

| # | 模块 | 缺失功能 | 重要性 | 对体验 / 业务的影响 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| 1 | 身份与权限 | **认证与鉴权体系**（登录 / API Key / 会话归属） | 极高 | 无身份则无法多人共享、无法做配额与审计；这是从「自用脚本」走向「可用产品」的分水岭 | **P0** |
| 2 | 运行控制 | **用户主动中止运行**（stop / 取消端点） | 极高 | 长任务无法打断 = 用户被锁死；竞品全部具备，属基础交互契约 | **P0** |
| 3 | 可观测性 | **审计日志**（审批决策、工具执行、越权拒绝落库） | 极高 | 安全事件不可追溯，留不出「谁批了什么」的证据链 | **P0** |
| 4 | 工程保障 | **自动化测试套件**（当前 0 个测试文件，仅 1 个 smoke 脚本） | 极高 | 内核逻辑无回归网，任何重构都是高风险 | **P0** |
| 5 | 工具扩展 | **联网检索 / 网页抓取工具** | 高 | Agent 信息获取能力为零，直接限制可解任务的类型 | **P1** |
| 6 | 模型层 | **多 Provider 注册与故障转移** | 高 | 单供应商锁定 + 单点故障；抽象已就位，性价比极高 | **P1** |
| 7 | 成本管理 | **Token / 费用统计与用量配额** | 高 | 无法衡量单次任务 ROI，无法设限额，成本黑洞 | **P1** |
| 8 | 会话管理 | **重命名 / 搜索 / 归档 / 标签** | 高 | 会话积累后清单迅速退化成噪声，历史资产不可用 | **P1** |
| 9 | 内容交互 | **消息编辑 / 重新生成 / 分支对话** | 高 | 试错成本高，一次不满意必须重开会话 | **P1** |
| 10 | 可观测性 | **健康检查、指标端点、链路追踪** | 高 | 无法部署到需要探活与监控的环境 | **P1** |
| 11 | 工具扩展 | **MCP / 自定义工具注册机制**（T8 已交付） | 高 | 决定生态天花板；没有它，每加一个能力都要改内核。现已支持配置化 MCP server + 自定义工具模块，冲突在装配期显式报错 | 已完成 |
| 12 | 记忆层 | **长期记忆持久化 + 记忆管理**（T9 已交付） | 高 | 此前「跨会话记忆」重启即丢、且所有用户共用一个记忆池；现已换 SQLite Store、按主体隔离命名空间，并提供查看/删除面板 | 已完成 |
| 13 | 文件与产物 | **工作区文件浏览器 / 完整输出查看** | 中高 | 无法校验 Agent 产物，只能「信它说的」 | **P1** |
| 14 | 运行治理 | **全局并发上限、按用户限流**（T7 已交付运行超时与中断 TTL） | 中高 | 多用户下资源可被单用户耗尽；审批提醒仍缺 | **P1** |
| 15 | 提示工程 | **可配置系统提示词 / 角色模板** | 中高 | 提示词硬编码，无法把 Agent 调教成特定岗位 | **P2** |
| 16 | 输入能力 | **文件上传与多模态输入** | 中 | 「帮我看看这份 PDF / 这张图」类需求无法承接 | **P2** |
| 17 | 自动化 | **定时任务 / 后台作业 / 事件触发** | 中 | 只能人机同步对话，无法做巡检、定时报告 | **P2** |
| 18 | 数据治理 | **数据库迁移机制、检查点归档与清理** | 中 | 表结构演进无版本管理，`.data/agent.db` 会无限膨胀 | **P2** |

| 22 | 沙箱能力 | **`docker` 沙箱档位（Tier 2）** | 中 | Tier 0/1 均「非安全边界」，缺 Tier 2 则难以对公网放宽审批 | **P2** |
| 23 | 前端体验 | **错误重试、流式失败续接、Markdown 渲染** | 中 | 错误仅 append 文本无重试入口；助手消息纯文本渲染，代码 / 表格不可读 | **P2** |
| 24 | 工程交付 | **Dockerfile / compose / CI 流水线** | 中 | 部署靠手搓，环境不可复现，无自动质量门禁 | **P2** |
| 25 | 交互细节 | **草稿态持久化**（未发送输入不丢） | 低 | 刷新即丢未发送内容，长文本输入痛感明显 | **P3** |
| 26 | 国际化 | **前端 i18n** | 低 | 界面与提示词硬编码中文 | **P3** |
| 27 | 移动端 | **响应式布局 / 移动端适配** | 低 | 窄屏可用性未验证，影响碎片化使用 | **P3** |

## 四、优先级矩阵（投入产出视角）

```
高影响 ┤  ① 鉴权   ② 中止      ③ 审计   ④ 测试
       │   ★ 先做：低成本、解阻塞
       │
       │  ⑥ 多 Provider  ⑤ 检索  ⑫ 记忆  ⑧ 会话管理
       │  ⑦ 用量  ⑩ 运维  ⑪ MCP  ⑬ 文件面板  ⑭ 治理
       │   ★ 次做：决定产品竞争力
       │
低影响 ┤  ⑮ 提示词  ⑯ 多模态  ⑰ 定时  ⑱ 迁移  ⑲ RAG
       │  ⑳ 技能  ㉑ 导出  ㉒ Tier2  ㉓ UI  ㉔ 容器
       │  ㉕ 草稿  ㉖ i18n  ㉗ 移动端
       └────────────────────────────────────────
          低成本 ──────────────────── 高成本
```

### 建议推进节奏

**第一梯队（解阻塞）** — ① 鉴权 → ② 中止 → ③ 审计 → ④ 测试
不做完这四项，产品无法交到第二个人手里。

**第二梯队（补短板）** — ⑥ 多 Provider（抽象已就位，竞争力提升成本最低）→ ⑤ 联网检索 → ⑫ 记忆持久化 → ⑧ 会话搜索 / 重命名 → ⑩ 健康检查 → ⑦ 用量统计

**第三梯队（建壁垒）** — ⑪ MCP（T8 已交付）→ ⑫ 记忆持久化（T9 已交付）→ ⑲ RAG → ⑳ 技能库 → ⑰ 定时任务 → ㉒ Docker 沙箱

## 五、结论

当前项目的**内核与安全设计是超额完成的**（分层、护栏、沙箱、HITL 都做到了生产级思考），但**「人」的那一侧——身份、控制、可见性、可运维——几乎为零**。

接下来最该补的不是更强的 Agent 能力，而是让这个已经很强的内核变得**可被信任、可被中断、可被计量、可被追溯**。

其中第 ① 项「认证与鉴权体系」是所有后续能力（用量配额、审计、会话归属、协作分享）的**前置依赖**，应作为第一优先级；其技术选型与实现形式详见同目录下的 `认证与鉴权体系.md`。
