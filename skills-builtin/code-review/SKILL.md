# 代码审查

## 何时使用

- 用户要求审查某个文件、某个目录或某段实现
- 用户要求在改动之前评估影响面

## 流程

1. 用 `glob` / `ls` 定位目标文件。用户没指定范围时**先问清楚**——默认扫全工作区既慢，
   又会把大量无关文件拉进上下文。
2. 逐个 `read_file` 读取。文件较长时先用 `grep` 定位关键定义（函数、类、配置项、错误
   分支），再读上下文，而不是整篇通读。
3. 按下面四类各给一条结论（该类没问题就写「无」，不要省略）：
   - **正确性**：边界条件、错误处理、并发与状态
   - **安全**：输入校验、凭据处理、权限边界
   - **可维护性**：命名、重复、过深嵌套
   - **测试**：明显未被覆盖的分支
4. 每条问题给出四样东西：**位置**（文件与行号）、现象、为什么是问题、怎么改。只给结论
   不给位置等于让人自己去找，那和没审一样。
5. 最后一行给总体判断：可以直接用 / 改完再看。

## 边界

- **只读不写**：审查本身不修改文件，除非用户明确要求你顺手改掉。
- 不臆测没读到的代码。没打开过的文件不要下结论。
